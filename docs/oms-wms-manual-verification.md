# OMS-WMS 통합 수동 검증

통합 시나리오의 기준본은 OMS 저장소에서 관리한다.

- GitHub: [manual-verification-scenarios.md](https://github.com/twin10240/jhg-commerce-project/blob/master/docs/manual-verification-scenarios.md)
- 로컬: `../jhg-commerce-project/docs/manual-verification-scenarios.md`

WMS 변경을 검증할 때도 기준본의 로그인·API 401·부분입고·발주 취소·원장·권한·대시보드
시나리오를 사용한다. 결과와 캡처는 기준본의 검증 기록 표에 한 번만 기록한다.

## 개발 DB 초기화 절차 (OMS·WMS 동시)

OMS(`~/hgpage`)와 WMS(`PostgreSQL wms`)는 물리적으로 다른 DB이고 `orderId` 시퀀스도 각자 센다.
**한쪽만 초기화하면 `orderId`가 재사용되어 과거 예약이 새 주문의 예약으로 오인된다.**
(실제 사고: OMS 주문 52 = 상품1×1·상품2×2인데 WMS에는 상품2×1 `SHIPPED` 예약 52가 남아 있었다.)

초기화는 항상 **두 앱을 함께** 수행한다.

1. 두 앱을 모두 중단한다.
2. OMS를 `--spring.profiles.active=local`로 기동해 스키마를 재생성한다(`ddl-auto: create`).
3. WMS도 `--spring.profiles.active=local`로 기동해 스키마를 재생성한다.
   WMS는 V3.0부터 PostgreSQL 17을 쓴다 — 먼저 `brew services start postgresql@17`이 떠 있어야 한다.
   개발용은 `wms`, 테스트용은 `wms_test` 데이터베이스다.
4. 두 앱을 평소 프로파일로 재기동한다.

한쪽만 초기화한 상태에서 예약이 들어오면 `reserveAll`이 **409 "orderId 예약 원장 불일치"** 로 거부한다.
이 오류를 보면 코드가 아니라 DB 상태 문제이므로 위 절차로 양쪽을 함께 초기화한다.
이미 어긋난 과거 예약 행은 코드로 복구되지 않으므로 별도로 정리해야 한다.

## WMS 단독 실행 기록

시나리오 정의와 상세 결과는 기준본에 두고, 여기에는 **WMS 저장소에서 언제·무엇을 돌렸는지**만 남긴다.

### 2026-07-26 — WMS 단독 시나리오 32/32 통과

- **범위**: 로그인·로그아웃 / API 401 / 보충요청 승인·반려 / 부분입고·전량입고 / 부분입고 발주 취소 / 재고 조정·원장 / 이력 화면·필터 / 권한 / 대시보드 집계
- **방법**: Playwright 헤드리스로 실제 화면을 조작하고 상태를 단언, API 인증은 `curl`. 자동화 스크립트는 일회성이라 저장소에 두지 않는다.
- **환경**: `local` 프로파일로 스키마를 리셋해 클린 상태에서 시작. **OMS는 중단** — 보상 스윕(60초 주기)이 WMS에 예약을 걸어 대시보드 집계 대조를 오염시키기 때문.
- **결과**: 단언 32건 전부 통과. 주요 확인 —
  - 취소: 발주 `CANCELLED` + 연결 요청 `CANCELLED` + **입고분 보존** + **신규 원장 행 없음** + 입고 수단 미노출
  - 부분입고 중 요청은 `APPROVED` 유지, 전량입고 시점에만 `FULFILLED`
  - `/api/**` 미인증 401이며 `Location` 헤더 없음(폼 로그인 리다이렉트로 새지 않음)
  - OPERATOR가 MANAGER 액션을 직접 POST하면 403
- **후속 조치**: 취소·완료 발주 상세에 "이번 입고" 입력칸이 남던 것을 진행 중 상태에서만 렌더하도록 수정.

### 2026-07-26 — 반응형 확인 (375px·1280px)

Chrome 기기 툴바로 주요 관리자 화면(대시보드·재고·재고 이력·발주 목록·발주 상세·보충 요청)을 375px와 1280px에서 확인.
**레이아웃 이상 없음** — 컬럼이 많은 표(발주 목록 9열, 재고 이력 7열)도 페이지 본문이 밀리지 않고 표 자체 컨테이너 안에서만 가로 스크롤(`.table-wrap`)되는 것을 확인.

**미수행(범위 밖)** — OMS 연동(주문·취소·백오더·FIFO·출고), 장애와 복구, 최종 화면·반응형.
이들은 두 앱을 함께 띄워야 하므로 기준본 절차로 수행하고 결과도 기준본에 기록한다.

### 2026-08-27 — 수불대장 원장 불변식 표시 (V3.0, WMS 단독)

`Σdelta == onHand`를 화면에서 대조하는 기능(`/admin/inventory/ledger`)을 4갈래로 확인했다.
정상 사용으로는 불변식이 깨지지 않으므로(모든 재고 변경이 `applyDelta` 하나를 지나며 원장을 함께 쓴다)
위반 경로는 DB를 직접 건드려 만들어야 한다.

| # | 시나리오 | 조작 | 기대 |
|---|---|---|---|
| ① | 일치 | 기본 기간(이번 달 1일~오늘)으로 조회 | "✓ 원장 합계와 실제 보유수량이 일치합니다." |
| ② | 과거 기간은 대조 안 함 | 종료일을 어제로 변경 | 초록·빨강 **모두 미표시** (기말재고는 그 시점 값이라 현재 onHand와 달라야 정상 — 대조하면 거짓 경고) |
| ③ | 수량 불일치 | `UPDATE inventory SET on_hand_qty = on_hand_qty + 3 WHERE product_id = 1` | 빨간 경고 + 상품1 / 원장 15 / 실제 18 / 차이 3 |
| ④ | 원장 없는 재고 | `INSERT INTO inventory (inventory_id, product_id, product_name, on_hand_qty, reserved_qty, version) VALUES (9999, 9999, '검증용', 7, 0, 0)` | 빨간 경고 + 검증용 / 원장 0 / 실제 7 / 차이 7. **본표에는 9999가 안 나옴**(거래가 없어 등장 근거 없음)인데도 경고에는 잡혀야 한다 |

정리: ③은 `- 3`으로 되돌리고, ④는 `DELETE FROM inventory WHERE product_id = 9999`.
정리 후 아래 쿼리가 0행이어야 한다.

```sql
select i.product_id, i.on_hand_qty, coalesce(sum(a.delta),0)
from inventory i left join inventory_adjustment a on a.product_id = i.product_id
group by i.product_id, i.on_hand_qty
having i.on_hand_qty <> coalesce(sum(a.delta),0);
```

**발견하고 고친 것**: 위반 표의 숫자 열이 `td`에만 우측 정렬돼 있어 머리글과 값이 어긋났다
(`admin.css`의 `th, td`가 left 정렬). 또 경고 블록이 `.table-wrap` 안에 있어 10열 본표 폭에 맞춰
가로 스크롤되는 영역에 갇혀 있었다. 둘 다 수정.

**환경 이슈(재확인)**: 템플릿만 고치고 앱을 재기동하지 않으면 반영되지 않는다
(devtools 없음, `spring.thymeleaf.cache` 기본값 = 켜짐, IntelliJ 실행은 `build/resources/main`을 읽는다).

### 2026-08-26 — 실사 중 수동 조정 차단 (WMS 단독, 부분)

가드를 넣은 뒤 실행 중이던 앱이 옛 빌드라 조정이 통과한 것을 발견 → 재기동 후 확인.
**세션 54(상품1, 계수 14, `SUBMITTED`)** 상태에서 4건을 확인했고 전부 기대값이었다.

| # | 시나리오 | 결과 |
|---|---|---|
| ① | 실사 중인 상품1 수동 조정 | 거부 — "실사가 진행 중인 상품은 조정할 수 없습니다" |
| ② | 실사에 없는 상품 조정 | 통과 |
| ③ | `manager`로 세션 54 승인 | 차이 0 → 원장 행 없이 "일치" |
| ④ | 승인 후 상품1 조정 | 통과 (종결된 세션은 잠그지 않음) |

**환경 이슈(기록용)**: 코드 변경 후 앱을 재기동하지 않으면 가드가 적용되지 않는다.
검증 전 재기동 여부를 먼저 확인할 것.

**데이터 정정**: 옛 빌드로 통과한 상품1 조정 `+1`(원장 #203)을 보상 조정 `-1`(원장 #301, actor `system`)로
되돌렸다. 원장 행은 지우지 않았다 — `Σdelta == onHand` 불변식을 유지하기 위해서다.

**아직 안 한 것**: 실사 전체 시나리오(세션 개설·겹침 거부·부분 입력 제출 거부·자기승인 차단·반려 경로·
계수 중 재고 이동 후 승인·재고 증가 시 OMS 백오더 승격)와 반려 모달 확인, 신규 화면 5개 375px 확인.

### 2026-08-15 — V2 반품(RMA) 계약 스모크 (WMS 단독)

`feat/wms-v2` 브랜치를 로컬 기동해 `curl`로 확인. OMS는 떠 있었지만 반품 콜백 수신부가 없던 시점이라
**통지 실패 경로까지 함께 관측**됐다.

- **API 계약 7건 전부 기대값**: 신규 접수 `201` / 같은 키·같은 내용 `200` / 같은 키·다른 내용 `409` /
  수량 0 `400` / 누적 반품량 초과 `400` / 없는 RMA 조회 `404` / 미인증 `401`
- **검수·재고**: 상품1 `16 → 출고 2 → 14 → 승인 1 재입고 → 15`, 원장에 `반품 +1 (14→15) RMA #102` 한 행
- **입력 강제**: 승인 수량 없이 제출하면 `모든 품목의 승인 수량과 처분을 입력해야 합니다.`로 거부되고 상태 불변
- **누적 반품량 규칙**: 접수 직후 추가 1개 요청은 `400`, 검수에서 1개만 승인되자 같은 요청이 `201`
  (거절분 재신청 가능), 그 다음 1개는 다시 `400`
- **콜백 best-effort**: OMS에 수신 엔드포인트가 없어 `OMS 반품 결과 통지 실패(무시)` 경고가 남았으나
  재입고와 `COMPLETED`는 그대로 커밋됨

### 2026-08-15 — OMS·WMS 통합 V2-1~V2-4 (기준본 시나리오)

OMS `feature/oms-v2-rma` 워크트리(:8080)와 WMS `feat/wms-v2`(:8081)를 함께 띄워 수행.
**시나리오 정의와 상세 증거는 기준본에 기록**했고, 여기에는 WMS 쪽 관측만 남긴다.

- V2-1 전량 `RESTOCKED` → 재고 `70→72`, `RETURN` 원장 1행
- V2-2 부분 승인 + `REJECTED` → 승인분만 `91→92`, 거절 품목 `104→104` 불변, 원장 1행
- V2-3 `DISPOSED` → 재고 `118→118`, 원장 **0행**
- V2-4 `REQUESTED` 취소 → `CANCELLED`, 재고 불변, 원장 0행

**환경 이슈(기록용)**: OMS DB만 초기화돼 주문 ID가 1부터 다시 시작하는데 WMS에는 이전 `orderId 1~11`
예약이 남아 있어, 같은 `orderId`의 옛 예약과 충돌해 접수가 `400`으로 거부됐다. 두 시스템이 `orderId`를
공유 키로 쓰는 구조라 **한쪽만 리셋하면 안 된다** — 검증용 데이터는 양쪽을 함께 초기화해야 한다.
