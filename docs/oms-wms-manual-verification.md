# OMS-WMS 통합 수동 검증

통합 시나리오의 기준본은 OMS 저장소에서 관리한다.

- GitHub: [manual-verification-scenarios.md](https://github.com/twin10240/jhg-commerce-project/blob/master/docs/manual-verification-scenarios.md)
- 로컬: `../jhg-commerce-project/docs/manual-verification-scenarios.md`

WMS 변경을 검증할 때도 기준본의 로그인·API 401·부분입고·발주 취소·원장·권한·대시보드
시나리오를 사용한다. 결과와 캡처는 기준본의 검증 기록 표에 한 번만 기록한다.

## 개발 DB 초기화 절차 (OMS·WMS 동시)

OMS(`~/hgpage`)와 WMS(`PostgreSQL wms`)는 물리적으로 다른 DB이고 `orderId` 시퀀스도 각자 센다.
**한쪽만 초기화하면 `orderId`가 재사용되어 과거 예약이 새 주문의 예약으로 오인된다.**
(실제 사고: OMS 주문 52 = 상품1×1·상품2×2인데 WMS에는 상품2×1 `SHIPPED` 예약 52가 남아 있었다.)

초기화는 항상 **두 앱을 함께** 수행한다.

1. 두 앱을 모두 중단한다.
2. OMS를 `--spring.profiles.active=local`로 기동해 스키마를 재생성한다(`ddl-auto: create`).
3. WMS도 `--spring.profiles.active=local`로 기동해 스키마를 재생성한다.
   WMS는 V3.0부터 PostgreSQL 17을 쓴다 — 먼저 `brew services start postgresql@17`이 떠 있어야 한다.
   개발용은 `wms`, 테스트용은 `wms_test` 데이터베이스다.
4. 두 앱을 평소 프로파일로 재기동한다.

한쪽만 초기화한 상태에서 예약이 들어오면 `reserveAll`이 **409 "orderId 예약 원장 불일치"** 로 거부한다.
이 오류를 보면 코드가 아니라 DB 상태 문제이므로 위 절차로 양쪽을 함께 초기화한다.
이미 어긋난 과거 예약 행은 코드로 복구되지 않으므로 별도로 정리해야 한다.

## WMS 단독 실행 기록

시나리오 정의와 상세 결과는 기준본에 두고, 여기에는 **WMS 저장소에서 언제·무엇을 돌렸는지**만 남긴다.

### 2026-07-26 — WMS 단독 시나리오 32/32 통과

- **범위**: 로그인·로그아웃 / API 401 / 보충요청 승인·반려 / 부분입고·전량입고 / 부분입고 발주 취소 / 재고 조정·원장 / 이력 화면·필터 / 권한 / 대시보드 집계
- **방법**: Playwright 헤드리스로 실제 화면을 조작하고 상태를 단언, API 인증은 `curl`. 자동화 스크립트는 일회성이라 저장소에 두지 않는다.
- **환경**: `local` 프로파일로 스키마를 리셋해 클린 상태에서 시작. **OMS는 중단** — 보상 스윕(60초 주기)이 WMS에 예약을 걸어 대시보드 집계 대조를 오염시키기 때문.
- **결과**: 단언 32건 전부 통과. 주요 확인 —
  - 취소: 발주 `CANCELLED` + 연결 요청 `CANCELLED` + **입고분 보존** + **신규 원장 행 없음** + 입고 수단 미노출
  - 부분입고 중 요청은 `APPROVED` 유지, 전량입고 시점에만 `FULFILLED`
  - `/api/**` 미인증 401이며 `Location` 헤더 없음(폼 로그인 리다이렉트로 새지 않음)
  - OPERATOR가 MANAGER 액션을 직접 POST하면 403
- **후속 조치**: 취소·완료 발주 상세에 "이번 입고" 입력칸이 남던 것을 진행 중 상태에서만 렌더하도록 수정.

### 2026-07-26 — 반응형 확인 (375px·1280px)

Chrome 기기 툴바로 주요 관리자 화면(대시보드·재고·재고 이력·발주 목록·발주 상세·보충 요청)을 375px와 1280px에서 확인.
**레이아웃 이상 없음** — 컬럼이 많은 표(발주 목록 9열, 재고 이력 7열)도 페이지 본문이 밀리지 않고 표 자체 컨테이너 안에서만 가로 스크롤(`.table-wrap`)되는 것을 확인.

**미수행(범위 밖)** — OMS 연동(주문·취소·백오더·FIFO·출고), 장애와 복구, 최종 화면·반응형.
이들은 두 앱을 함께 띄워야 하므로 기준본 절차로 수행하고 결과도 기준본에 기록한다.

### 2026-08-27 — 대시보드 집계 대조 · 권한 · 인증 (WMS 단독)

포트폴리오 1차 검증 대기 항목 중 남아 있던 3건. **전부 기대값이었다.**

**① 대시보드 집계 ↔ 목록 건수 대조**

대시보드가 목록과 따로 집계하므로 어긋날 수 있는 지점이다. 확인 시점 개발 DB 값:

| 항목 | 값 | 항목 | 값 |
|---|---|---|---|
| SKU 수 | 20 | 예약 RESERVED | 1 |
| 총 보유 | 3150 | 예약 SHIPPED | 2 |
| 총 예약 | 16 | 반품 COMPLETED | 2 |
| 총 가용 | 3134 | 나머지 상태 | 0 |

`총 보유 - 총 예약 = 총 가용`(3150 − 16 = 3134)도 성립. 상태별 건수는 각 목록의
`?status=` 필터 결과와 일치.

**한계(기록용)**: 15개 지표 중 10개가 0이었다. 0끼리의 일치는 집계 로직이 어긋나도
드러나지 않는다. 각 상태에 최소 1건씩 채운 뒤 다시 보면 대조의 변별력이 생긴다.

**② OPERATOR 버튼 미노출 + 직접 POST 403**

`operator` 로그인 시 MANAGER 전용 9개 액션(발주 생성·취소, 보충요청 승인·반려,
반품 입고·완료·취소, 실사 승인·반려) 버튼 미노출. 버튼을 우회해 직접 POST해도 403.

재고 조정(`POST /admin/inventory/adjust`)은 OPERATOR에게도 보이고 통과하는 것이 정상 —
의도된 설계다. 파손·오차를 현장에서 즉시 보정해야 하므로 MANAGER 전용으로 두지 않았고,
통제는 사전 승인이 아니라 ADJUST 원장에 actor가 남는 사후 추적이다.

**③ 로그인·로그아웃 + API 401**

로그인 성공·실패, 미인증 시 `/login` 리다이렉트, 로그아웃 후 뒤로가기 시 재로그인 요구 확인.
`/api/**`는 미인증 401, 서비스 계정 Basic(`wms`/`wms`)으로는 200.

401이 중요한 이유는 `/api/**`가 별도 체인이라 인증 실패 시 폼 로그인으로 302 리다이렉트되면
OMS가 "인증 실패"로 해석하지 못하기 때문이다(`HttpStatusEntryPoint`).

**참고**: ②③은 `WmsAdminControllerTest`·`SecurityChainIntegrationTest`가 이미 자동으로 덮는다.
이번 수동 확인은 실제 브라우저·실제 서블릿에서도 같은지를 본 것이다.

### 2026-08-30 — OMS·WMS 통합 (V3.1 송장·배송, 반품 입고 통지)

두 앱을 함께 띄워(OMS :8080 / WMS :8081, WMS는 PostgreSQL) 실제 화면·API로 수행.
**아래 세 흐름 모두 통과.**

**① 출고 송장 발급 → 배송 완료(S6)** — `orderId=455`, 상품14
주문 → 결제 승인 → 예약 확보(보유 210, 예약 1) → OMS 출고 → 실물·예약 동시 차감(보유 209, 예약 0)
→ WMS 송장 발급 `MOCK-455-20260830011457`(테스트택배) → OMS 주문 화면에 송장번호 표시
→ **WMS 관리자 배송 완료** → `deliveredAt` 기록 + S6 통지 → OMS `배송 완료` 반영, 재고 무변동.
같은 배송 완료를 다시 눌러도 OMS 상태·재고 불변(재통지 멱등).

**② 반품 입고 통지(`RECEIVED`)** — `returnId=302` / `rmaId=152`
V2.1에서 넣은 뒤 단위 테스트로만 확인했던 항목을 처음으로 E2E 검증했다.
고객 신청 → OMS 관리자 승인 → WMS 접수 → **WMS 입고 처리** → OMS 반품 화면의 진행 단계가
`창고 도착`으로 전환됨을 확인. 이 시점 재고는 불변(입고는 상태 전이일 뿐)이고,
이어서 검수 완료(승인 1, `RESTOCKED`) 시 보유 209 → 210으로 재입고, OMS 품목 결과에
`상품14 요청 1 승인 1 재입고` 표시.

**③ 오버셀 가드 실측** — 상품10(가용 150)에 151 예약 요청 → `false`, 예약 행 0건, 재고 불변.

**④ 배송 완료 소유권과 수동 보정 경로** — 배송 완료는 WMS가 관리하고, OMS 관리자 버튼은
수동 보정용이다. 두 경로가 갈렸을 때 서로 따라잡을 수 있는지를 확인했고 **양방향 모두 수렴한다.**

- OMS가 먼저 보정(`orderId=454`, WMS `deliveredAt = null`) → WMS 배송 완료 실행 → `deliveredAt` 기록,
  OMS는 이미 배송 완료라 뒤집히지 않음
- WMS가 먼저 기록(`orderId=455`) → OMS 수동 보정을 또 눌러도 WMS `deliveredAt` 불변

**⑤ 송장·배송 완료 경계** — 전부 기대대로 거부·멱등.

| 경계 | 결과 |
|------|------|
| 출고 안 된 주문에 배송 완료 | 거부, `deliveredAt` 없음 (`orderId=456` RESERVED 상태) |
| 출고 재요청 | 송장·발급시각 동일 — 재발급 없음 |
| 배송 완료 재요청 | `deliveredAt` 불변, OMS 재통지만 발생 |
| 송장 없는 구 출고 주문에 배송 완료 | 거부 (`markDelivered`가 송장 없으면 막는다) |
| 그 주문의 회복 | `ship` 재호출로 송장만 발급(`orderId=152`) → 배송 완료 성공. **재고는 다시 깎이지 않았다** — `ORDER#152` SHIP 원장은 08-27 한 줄 그대로이고 불변식 위반 0건 |

마지막 항목이 `shipAll`의 "조기 return을 없앤 이유: 이미 출고됐지만 송장이 없는 기존 주문이 여기
도달해야 한다"는 주석이 실제로 동작함을 보인다. 이미 `SHIPPED`면 원장 기록 블록을 건너뛰고
송장만 발급한다.

**발견 2 — dev DB에 가용 음수. 원인은 한쪽만 리셋된 것이다.**
상품1이 `보유 15 / 예약 16 / 가용 -1`. 원장 불변식(Σdelta == onHand)은 20개 상품 전부 정상이고
`reserved_qty`도 예약 원장과 일치하므로 **집계 오류가 아니다.**

이 예약(`reservation_id=52`)은 OMS `orderId=2`의 것이고, **그 주문은 2026-08-25 결제 완료·재고 확보
상태로 살아 있다**(상품1 × 16, 160,000원). 상품1의 WMS 원장은 08-27 재시드 `OPENING +15` 한 줄뿐이다.
즉 결제된 주문의 예약은 남은 채 **WMS 재고만 15로 리셋**되어 어긋났다.

따라서 WMS 예약만 지우면 결제된 주문이 예약 없이 남아 출고 시 `예약이 없어 출고할 수 없습니다`로
막힌다. 정리는 OMS 주문 취소(→ `/api/inventory/release`) 경로로 양쪽을 함께 되돌려야 한다.
현행 코드의 오버셀 가드 자체는 ③으로 정상 동작을 확인했다.

**⑥ 결제 완료 주문 취소 → WMS 예약 해제** (V1 시나리오 4 재검증 · 위 ⑤의 정리를 겸함)

V1 시나리오 4는 2026-08-04에 통과했지만 그 뒤 OMS에 결제(08-21~25)가 들어와 흐름이 바뀌었다.
결제 완료 주문의 취소는 이제 **환불과 예약 해제가 함께** 일어난다. 위 `orderId=2`를 대상으로
강제 삭제가 아니라 실제 취소 경로로 정리하면서 함께 검증했다.

| | 취소 전 | 취소 후 |
|---|---|---|
| WMS 상품1 | 보유 15 / 예약 16 / **가용 -1** | 보유 15 / 예약 0 / **가용 15** |
| WMS 예약(id 52) | `RESERVED` | `RELEASED` |
| OMS 주문2 | 재고 확보 · 결제 완료 | 주문 취소 · **누적 환불 160,000원 환불 완료** |

고객 취소 후 `CancellationSweeper`(5초 주기)가 **4초 만에** WMS `release`를 호출해 해제됐다.
확인 사항: 보유 수량 무변동, 상품1 원장 1행 그대로(해제는 `onHand`를 건드리지 않으므로 원장을
남기지 않는 것이 맞다), 불변식 위반 0건, 전 상품 가용 음수 0건, `reserved_qty`와 예약 원장 합 일치.

억지로 지웠다면 결제된 주문이 예약 없이 남았을 것이다. 정리 방법을 바꾼 판단이 옳았고,
그 김에 결제 도입 후 한 번도 밟지 않았던 취소 경로를 처음으로 확인했다.

**⑦ WMS 중단 중 주문·결제 → 복구 후 예약 확보** (`AllocationSweeper`, 08-21 신설 후 첫 검증)

WMS를 실제로 내리고 그 상태에서 주문·결제한 뒤 다시 띄워 관측했다.

- **중단 중에도 주문과 결제는 성공한다.** 주문은 실패하지 않고 `재고 확인 중`으로 대기한다
  (`orderId=502` 상품16, `orderId=503` 상품17 — 둘 다 결제 완료 상태로 보존).
- **복구 후 예약이 자동으로 잡힌다.** 502는 약 5분, 503은 약 15초 만에 확보됐다.
  차이는 두 회수 경로 때문이다 — `AllocationSweeper.sweep()`은 5초마다
  `recoverStaleAllocations(now - allocation.processing-timeout)`(기본 **5분**)로 처리 중에 멈춘 건을
  회수하고, 그와 별개로 `findDueAllocationOrderIds(now)`로 재시도 예정 건을 바로 처리한다.
  처리 중 상태로 멈춘 건은 5분을 기다려야 하고, 재시도 예약된 건은 다음 스윕에 바로 잡힌다.
- 검증 후 전 상품 가용 음수 0건, 불변식 위반 0건.

**⑧ 백오더 → 보충 요청 → 승인·발주 → 입고 → FIFO 승격** (V1 시나리오 5·6·8 재검증)

결제 도입 후 처음으로 전 사슬을 한 번에 돌렸다. 상품1(가용 15)에 20개를 주문해 백오더를 만든 뒤,
OMS 관리자 보충 요청 → WMS 승인 → 발주 → 입고까지 실제 화면으로 진행했다.

| 단계 | 결과 |
|------|------|
| 가용 초과 주문(20 > 15) + 결제 | `orderId=504` **결제 완료 · 입고 대기** — 주문이 거부되지 않고 백오더로 접수 |
| OMS → WMS 보충 요청 | WMS에 `검토 대기`로 접수(상품#1, 20개) |
| WMS 승인 | 요청 `발주 진행`, 발주 1건 생성(`0 / 20`) |

### 2026-08-27 — 수불대장 원장 불변식 표시 (V3.0, WMS 단독)

`Σdelta == onHand`를 화면에서 대조하는 기능(`/admin/inventory/ledger`)을 4갈래로 확인했다.
정상 사용으로는 불변식이 깨지지 않으므로(모든 재고 변경이 `applyDelta` 하나를 지나며 원장을 함께 쓴다)
위반 경로는 DB를 직접 건드려 만들어야 한다.

| # | 시나리오 | 조작 | 기대 |
|---|---|---|---|
| ① | 일치 | 기본 기간(이번 달 1일~오늘)으로 조회 | "✓ 원장 합계와 실제 보유수량이 일치합니다." |
| ② | 과거 기간은 대조 안 함 | 종료일을 어제로 변경 | 초록·빨강 **모두 미표시** (기말재고는 그 시점 값이라 현재 onHand와 달라야 정상 — 대조하면 거짓 경고) |
| ③ | 수량 불일치 | `UPDATE inventory SET on_hand_qty = on_hand_qty + 3 WHERE product_id = 1` | 빨간 경고 + 상품1 / 원장 15 / 실제 18 / 차이 3 |
| ④ | 원장 없는 재고 | `INSERT INTO inventory (inventory_id, product_id, product_name, on_hand_qty, reserved_qty, version) VALUES (9999, 9999, '검증용', 7, 0, 0)` | 빨간 경고 + 검증용 / 원장 0 / 실제 7 / 차이 7. **본표에는 9999가 안 나옴**(거래가 없어 등장 근거 없음)인데도 경고에는 잡혀야 한다 |

정리: ③은 `- 3`으로 되돌리고, ④는 `DELETE FROM inventory WHERE product_id = 9999`.
정리 후 아래 쿼리가 0행이어야 한다.

```sql
select i.product_id, i.on_hand_qty, coalesce(sum(a.delta),0)
from inventory i left join inventory_adjustment a on a.product_id = i.product_id
group by i.product_id, i.on_hand_qty
having i.on_hand_qty <> coalesce(sum(a.delta),0);
```

**발견하고 고친 것**: 위반 표의 숫자 열이 `td`에만 우측 정렬돼 있어 머리글과 값이 어긋났다
(`admin.css`의 `th, td`가 left 정렬). 또 경고 블록이 `.table-wrap` 안에 있어 10열 본표 폭에 맞춰
가로 스크롤되는 영역에 갇혀 있었다. 둘 다 수정.

**환경 이슈(재확인)**: 템플릿만 고치고 앱을 재기동하지 않으면 반영되지 않는다

   |---|---|
   | `반품 사유 분류: rmaId=.. category=.. confidence=.. model=.. in=.. out=..` | 성공 |
   | `반품 사유 분류 호출 실패(무시): ...` | API 호출 자체가 실패(타임아웃·연결 실패·SDK 예외 — 잘못된 요청 모양으로 인한 400도 여기 포함) |
   | `분류 응답이 비어 있음(무시)` | 응답은 왔지만 텍스트 블록이 없음 |
   | `분류 응답이 스키마를 벗어남(무시), 문제 필드: ...` | 모델이 우리가 거부하는 모양으로 응답(enum 이탈 등) |
   | `분류 응답 파싱 실패(무시): ... (응답 길이 ..)` | 응답 JSON 자체가 깨짐(잘림 등) |

   **위 실패 네 줄에는 모두 다음 줄이 함께 남는다** — `classify()`가 빈 결과를 반환했다는 공통 표시일
   뿐 그 자체로는 원인을 구분하지 못하며, 원인은 바로 위에 함께 찍힌 네 줄 중 하나가 말해준다.

   | 로그 줄 | 의미 |
   |---|---|
   | `반품 사유 분류 없음(무시): rmaId={}` | 위 네 실패 줄 중 하나와 항상 함께 남는다(단독으로는 원인 구분 불가) |

   **단건 스모크에서는 사실상 나타나지 않지만, "이 기능이 조용해지는 경로"의 목록에는 속하는 두 줄**도
   있다 — 동시 요청이 몰려 분류 전용 스레드 풀의 대기열이 찼을 때, 그리고 `classify()` 자체가 아니라
   그 바깥(예: 결과 저장 중)에서 예외가 났을 때다. 한 번의 요청으로 확인하는 이 절차에서 볼 가능성은
   낮으므로 결과 표에 기록할 항목으로 기대하지 않는다.

   | 로그 줄 | 의미 |
   |---|---|
   | `반품 사유 분류 대기열 포화(무시): rmaId={} — 이번 건은 분류하지 않습니다.` | 분류 전용 스레드 풀 대기열(50)이 가득 차 이번 건은 분류를 시도조차 하지 않음 |
   | `반품 사유 분류 실패(무시): rmaId={}` | `classify()` 밖(예: 저장 중)에서 예외 발생 — 호출 실패·빈 응답·스키마 이탈·파싱 실패와는 다른 지점 |

5. `/admin/returns/{id}` 에서 참고 영역이 한글 라벨로 보이고, **승인 수량·처분 입력칸이 비어 있는지** 확인

**기록할 것**: 분류 결과(category/confidence/evidence/처분 제안), 입력·출력 토큰, 접수 응답 체감 지연,
위 표에서 실제로 남은 로그 줄. 그리고 실제 호출로만 확인되는 두 가지 — 구조화 출력이 정말 텍스트
블록으로 도착했는지, `output_config.format` 요청 모양이 `claude-haiku-4-5` 상대로 400 없이 수락됐는지.

**결과 (2026-08-31, `RMA-SMOKE-1` / rmaId=302 / orderId=9001 / 사유 "받았는데 모서리가 깨져 있어요")**

| 항목 | 결과 |
|------|------|
| 접수 응답 지연 | **0.13초** — 201이 즉시 반환. 분류(약 8초 뒤 로그)를 기다리지 않는다 |
| category / confidence | `DAMAGED` / `HIGH` |
| evidence | `모서리가 깨져 있어요` (입력 사유에서 발췌) |
| 처분 제안 | `DISPOSED` |
| 입력 / 출력 토큰 | **984 / 35** |
| 입력칸 비어 있음 | ✅ 승인 수량·처분 모두 `—`. 참고 영역은 한글 라벨(파손 · 높음 · 폐기)로 표시 |
| 로그에 남은 줄 | 성공 한 줄만 — `반품 사유 분류: rmaId=302 category=DAMAGED confidence=HIGH model=claude-haiku-4-5-20251001 in=984 out=35` |
| 구조화 출력이 텍스트 블록으로 도착 | ✅ `TextBlock` 수집 → 파서 통과. 스키마 이탈·파싱 실패 줄 없음 |
| `output_config.format` 요청이 400 없이 수락됨 | ✅ `호출 실패(무시)` 줄이 남지 않음 |

- **모델 응답의 `model` 값은 별칭이 아니라 확정 스냅샷**이다 — 요청은 `claude-haiku-4-5`로 보내지만
  응답·저장값은 `claude-haiku-4-5-20251001`. 저장된 값으로 재현 대상 버전을 특정할 수 있다.
- **입력 토큰이 추정(약 400)의 2.5배인 984**로 나왔다. 시스템 프롬프트·스키마가 예상보다 크다.
  다만 출력이 추정(120)보다 적은 35라 건당 비용은 약 1.6원으로 `application.yml` 주석의 1.4원과
  거의 같다 — 비용 결론은 유효하고, 토큰 배분 추정만 틀렸다.

**⑫ 키 없이 기동**

`ANTHROPIC_API_KEY`를 지우고 기동 → 로그에 `ANTHROPIC_API_KEY 미설정 — 반품 사유 자동 분류를 끈 채로 기동합니다.`
접수는 정상 동작하고, 반품 상세에 참고 영역이 아예 렌더되지 않는지 확인.

**결과 (2026-08-31, `RMA-SMOKE-3` / rmaId=352 / 사유 "다른 색상이 왔어요")** — ✅ 통과.
기동 로그에 미설정 줄, 접수는 `201` 0.09초 정상, `return_classification` 행 없음, 상세 화면에 참고 영역 없음.

> **로그 인벤토리 보정**: 위 ⑪의 표는 `반품 사유 분류 없음(무시)`이 "네 실패 줄 중 하나와 항상 함께
> 남는다"고 적었으나, **키 미설정 기동에서는 이 줄이 단독으로 남는다.** NoOp 분류기가 실패가 아니라
> 정상적으로 empty를 반환하기 때문이다. 즉 단독으로 남았다면 원인 불명이 아니라 **"분류가 꺼져 있다"는
> 뜻**이고, 기동 로그의 미설정 줄과 짝지어 읽으면 구분된다.

**⑬ 사유가 빈 반품**

`"reason"` 없이 접수 → 분류 호출 자체가 없어야 한다(로그에 위 표들의 어느 줄도 남지 않음).

**결과 (2026-08-31, `RMA-SMOKE-2` / rmaId=303 / orderId=9002)** — ✅ 통과.
접수 `201` 0.07초, 분류 관련 로그 **한 줄도 없음**(`분류 없음(무시)`조차 남지 않는다 —
`classify()` 진입 전에 걸러지므로 ⑫와 구분된다), `return_classification` 행 없음, 화면에 참고 영역 없음.
