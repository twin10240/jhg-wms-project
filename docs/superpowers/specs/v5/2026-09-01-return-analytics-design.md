# 반품 분석 데이터 계층 — WMS V5.0 스펙

## 왜 이 기능인가

최종 목표는 **반품 보고서**다. 반품 사유를 분석해 반품을 줄이는 것이 목적이고,
그 보고서는 결국 MCP 서버를 통해 CLI에서 만들어질 것이다.

그렇다면 지금 만들 것은 보고서가 아니라 **보고서가 서 있을 데이터 층**이다.
이유는 하나다 — MCP에서 해석하는 모델은 **클라이언트**에 산다. WMS 안에 LLM 호출을
심으면 CLI 경로에서는 그 코드가 안 돌고, 같은 해석을 두 번 만든 꼴이 된다.
그래서 이 단계는 **LLM을 한 줄도 쓰지 않는다.**

| 부분 | 2단계(MCP)로 넘어가나 |
|---|---|
| 코호트 반품률 집계 | 그대로 도구가 된다 |
| 소관 분류 축 | 그대로 간다 — 도메인 판단이라 어디서든 유효 |
| 상품별 사유 원문 묶음 | 그대로 도구가 된다 |
| ~~앱 안에서 LLM 호출~~ | 안 간다. 그래서 만들지 않는다 |

이 단계가 끝나면 버려지는 코드가 없다.

## 경계

```
원장(inventory_adjustment) ──┐
                             ├──▶ ReturnAnalyticsService ──▶ 화면(숫자 표)
반품(rma_return)          ────┤                            └▶ [2단계] MCP 도구
분류(return_classification) ─┘
```

- **읽기 전용이다.** 재고·상태·분류를 만들지도 고치지도 않는다.
- **LLM 호출이 없다.** 과금 경로가 생기지 않고, 테스트가 전부 공짜다.
- **판정하지 않는다.** "반품이 몰렸다"의 임계값을 두지 않는다. 화면은 순서만 정하고
  판단은 사람이 한다. 아무도 조정하지 않는 손잡이를 만들지 않기 위해서다.

## 반품률의 정의 — 코호트

**기간 내 출고된 주문을 모수로, 그 주문에서 나온 반품을 센다.**

단순 비율(기간 내 반품 ÷ 기간 내 출고)을 쓰지 않는다. 반품은 출고보다 늦게 오므로
**출고가 늘면 분모만 먼저 커져 반품률이 가짜로 떨어진다.** 성장하는 상품일수록
안전해 보이는, 정확히 반대로 읽히는 지표가 된다.

```
분모  기간 내 SHIP 원장 행           → (orderId, productId, 수량)
분자  그 orderId들에서 나온 반품     → (productId, 요청수량), CANCELLED 제외
```

**분자를 `requestedQuantity`로 센다.** `acceptedQuantity`는 검수가 끝나야 채워지므로
접수·입고 단계 반품이 통째로 빠진다. 반품률은 "얼마나 돌아왔나"지 "얼마나 승인했나"가
아니다. 취소된 반품(`CANCELLED`)만 뺀다 — 그건 돌아오지 않은 것이다.

### 알려진 한계 — 미성숙 코호트

최근 기간일수록 아직 반품이 들어오는 중이라 과소평가된다. 숨기지 않고
**"관찰 경과: 기간 종료일로부터 N일"을 보고서 머리에 한 줄로 낸다.** 경과 7일짜리
코호트의 1%와 경과 60일짜리의 1%는 다른 수인데, 그 차이는 화면이 알려주지 않으면
읽는 사람이 알 수 없다.

행마다 내지 않는다. 코호트의 성숙도는 **기간의 성질**이지 상품의 성질이 아니다.
상품별로 같은 값을 스무 번 반복하면 표만 넓어진다.

보정하지 않는다. 보정하려면 반품 도착 지연 분포를 가정해야 하고, 그 가정은
지금 데이터로 세울 수 없다. 가정을 숨긴 보정값보다 경과일이 적힌 원값이 낫다.

## 데이터 유도

**출고 수량** — 원장에서 온다. 엔티티는 `InventoryTransaction`이고 테이블명은
`inventory_adjustment`다(원장 도입 전 이름이 남아 있다). `type = SHIP`이고
`reference`가 `ORDER#{orderId}` 형식이라 주문 단위로 묶을 수 있다.

- `delta`는 출고에서 음수다. 수량은 절댓값을 쓴다.
- `reference` 파싱이 실패한 행(형식이 다르거나 null)은 **버리지 않고 따로 센다.**
  조용히 빠지면 분모가 줄어 반품률이 과대평가된다. 화면에 "주문 연결 불가 출고 N건"으로 낸다.

**반품 수량** — `RmaReturn.orderId`로 위 코호트와 조인하고 `RmaReturnItem`에서
`productId`·`requestedQuantity`를 꺼낸다.

**범주** — `return_classification`을 `rmaReturnId`로 조인한다. V4.0에서 만든 테이블이다.

## 소관 — 창고가 줄일 수 있는 반품

이 축이 보고서가 WMS에서 나와야 하는 이유다. 창고가 **직접 통제할 수 있는 반품**을
분리해내는 건 다른 시스템이 못 한다.

| 범주 | 소관 | 창고가 줄일 수 있나 |
|---|---|---|
| `WRONG_ITEM` | 피킹·출고 | **예 — 창고 책임** |
| `DAMAGED` | 포장·운송 | **일부 — 포장 개선** |
| `CHANGED_MIND` | 상품 정보 | 아니오 (MD 소관, 근거는 준다) |
| `OTHER` | 창고 밖 | 아니오 (배송·CS·결제) |

**설정으로 빼지 않는다.** 도메인 판단이지 취향이 아니다. 자바 enum(`ReturnOwnerArea`)에
고정하고 `ReturnCategory`에서 유도한다.

이 매핑이 기대는 분류 품질은 1회차 평가에서 확인됐다 — `WRONG_ITEM` 7/7,
`DAMAGED` 7/7, `CHANGED_MIND` 8/8. 보고서가 기대는 세 축이 만점이었고,
약했던 `OTHER`(6/8)는 조치가 창고 밖이라 결론에 덜 영향을 준다.
근거: `docs/wms-classification-eval.md`.

## 미분류를 숨기지 않는다

현재 반품 18건 중 분류가 붙은 것은 4건이다. V4.0 이전 데이터와 분류 실패분이 있다.
범주 분포에 **"미분류 N건"을 명시**한다. 안 그러면 합계가 안 맞고, 4건짜리 분포를
18건의 그림으로 읽게 된다. 분모가 다른 두 숫자를 한 표에 놓을 때 생기는 사고다.

## 인터페이스

`ReturnAnalyticsService` — 서비스 하나, 메서드 셋.

| 메서드 | 반환 |
|---|---|
| `productReturnRates(from, to)` | 상품별 행 — 출고수량·반품수량·반품률 (+ 기간 공통 경과일) |
| `categoryBreakdown(from, to)` | 범주별 건수·소관·미분류 수 |
| `returnReasons(productId, from, to)` | 상품 하나의 사유 원문 묶음 (2단계 MCP 도구용) |

세 번째는 이 단계의 화면이 쓰지 않는다. 2단계에서 MCP 도구가 부를 조회이고,
지금 넣는 이유는 **집계와 원문 조회가 같은 코호트 정의를 공유해야 하기 때문**이다.
나중에 따로 만들면 두 정의가 갈라진다.

## 화면

`/admin/returns/report?from=&to=` — 숫자 표만. 수불대장(`/admin/inventory/ledger`)과
같은 패턴이다. 기본 기간은 최근 30일.

## 테스트

전부 실제 PostgreSQL에서 돈다(이 저장소 관례). API 호출이 없으므로 전 구간이 공짜다.

고정할 성질:
- 코호트 반품률이 기간 밖 출고를 분모에서 뺀다
- 취소된 반품이 분자에서 빠진다
- `reference` 파싱 실패 행이 버려지지 않고 별도로 세어진다
- 미분류 건수가 범주 분포와 따로 나온다
- 관찰 경과일이 기간 종료일 기준으로 계산된다

## 안 하는 것

- **LLM 호출**. 이 단계의 정의다.
- **금액 환산·매출 예측**. 판매액·마진은 OMS 소관이고 WMS에는 수량뿐이다.
  보고서는 "반품 N건 중 M건은 창고가 줄일 수 있다"까지 말하고 멈춘다.
- **조치의 실행**. 공급업체 연락도 상품 설명 수정도 사람이 한다.
- **시계열 비교("전월 대비")**. 회차가 쌓인 뒤 필요하면 그때.
- **자동 발송·스케줄**. 볼 때 만든다.

## 2단계로 미루는 결정

- MCP 노출 방식 — 앱 내장(Spring AI MCP) vs 별도 프로세스 + REST
- 도구 스키마
- **읽기 전용 강제.** 재고 조정이나 반품 상태 전이를 도구로 열면 대화 중 모델이
  창고 데이터를 바꿀 수 있다. V4.0에서 세운 "AI는 확정하지 않는다"가 깨지는 지점이
  정확히 거기다.

## 열린 문제

- 개발 DB의 반품 사유가 `test`·빈 값·서로 무관한 건들이라 **패턴이 있는 데이터가 없다.**
  이 단계는 숫자만 다루므로 지장이 없지만, 2단계에서 해석 품질을 보려면 시드가 필요하다.
- 출고 시점을 원장(`SHIP` 행의 `createdAt`)에서 잡는다. `Reservation.issuedAt`은
  송장 발급 시각이라 출고 후 별도로 채워지고 null일 수 있어 쓰지 않는다.
