# 재고 실사(Cycle Count) + 원장 행위자 — WMS V2.1 스펙

## 왜 이 둘을 함께 하나

"이 수량이 왜 이렇게 됐는지 역추적할 수 있다"가 이 시스템의 핵심 주장인데, 지금 두 곳이 비어 있다.

- **차이를 발견하는 절차가 없다.** 장부와 실물이 어긋나도 수동 `ADJUST`로 덮어쓸 뿐이다.
- **원장에 행위자가 없다.** `OPERATOR`/`MANAGER`를 나눠뒀지만 원장은 누가 했는지 남기지 않는다.

실사는 차이를 드러내고, 행위자 기록은 그 조정에 책임을 붙인다. 한 문장으로는
**"장부와 실물이 어긋났을 때, 누가 무엇을 근거로 맞췄는가"** 에 답하는 작업이다.

## 상태 흐름

```
OPEN ──(실물 입력·수정)── OPEN
  └──(제출: 전 품목 입력 필수)──▶ SUBMITTED
                                    ├──(승인)──▶ APPROVED   차이만 COUNT 원장
                                    └──(반려)──▶ REJECTED   장부 불변
```

`COUNTING` 상태는 두지 않는다. `OPEN`과 동작이 같아 전이만 늘고 얻는 것이 없다.
진행률은 `입력된 품목 / 대상 품목`으로 화면에서 계산한다.

`APPROVED`와 `REJECTED`는 종결 상태다. 반려된 세션을 다시 열지 않고 새 세션을 만든다 —
반려는 "이 계수를 믿지 못하겠다"는 뜻이므로 같은 실물 수량을 재사용할 이유가 없다.

### 입력 규칙

- `countedQty`는 **0 이상**. `0`은 "세어보니 없었다"는 유효한 결과이고, `null`(미입력)과 구분한다.
  반품 검수에서 겪은 것과 같은 함정이다 — 미입력을 0으로 받으면 안 센 품목이 조용히 확정된다.
- 제출은 대상 전 품목에 값이 있어야 통과한다. 화면 `required`는 브라우저만 막으므로 서버에서도 검증한다.
- 세션 생성 시 대상 상품은 **1개 이상**이어야 하고, 재고 행이 없는 `productId`는 거부한다.

## 차이의 기준 시점

**차이 = 실물 수량 − 승인 시점 장부 수량.**

실사는 세는 동안 시간이 흐르고, 그 사이 입출고가 계속된다. 승인 시점으로 재계산하면
원장 불변식(Σdelta == onHand)이 저절로 유지되고, 실사 때문에 출고를 막을 필요도 없다.

| 시점 | 장부 | 사건 |
|------|------|------|
| 세션 시작 | 15 | 대상 담기 |
| 실사 중 | 13 | 출고 2 |
| 실물 입력 | 13 | 담당자가 14를 셈 |
| 승인 | 13 → 14 | 차이 +1, `COUNT` 원장 1행 |

**한계(문서로 남길 것)**: 세는 동안 움직인 수량은 차이에 섞인다. 위 예에서 "실사 중 나간 2개"와
"원래 있던 오차"를 구분할 수 없다. 이를 구분하려면 대상 동결이 필요한데, 재고 정본을 한 곳에 둔
이 구조에서 동결은 OMS 주문 출고까지 막으므로 채택하지 않는다.

**보충(2026-08-26)**: 위 한계는 실제보다 온건하게 적혀 있었다. "섞인다"에 그치지 않고,
**계수와 승인 사이에 물건이 움직이면 실사가 장부를 더 망칠 수 있다.** 위 표는 유리한 순서
(출고 먼저, 계수 나중)만 보여준다. 순서를 뒤집으면 —

| 시점 | 장부 | 실물 | 사건 |
|------|------|------|------|
| 세션 시작 | 15 | 14 | 오차 1 |
| 실물 입력 | 15 | 14 | 담당자가 14를 셈 |
| 실사 중 | 13 | 12 | 출고 2 |
| 승인 | 13 → 14 | 12 | 차이 +1 반영 → **오차 2** |

계수는 특정 시점의 스냅샷인데 그것을 나중 시점에 절대값으로 덮어쓰기 때문이다.
근본 해결은 위치 단위 동결이고, 그건 로드맵 4번(위치·다중창고)이 들어와야 가능하다.

그 사이의 완화로 **수동 조정만 차단한다**(`CycleCountService.assertAdjustable`).
조정은 미룰 수 있어 막아도 비용이 없고, 승인이 계수값으로 덮어써서 조정 효과가 사라지는
혼선을 없앤다. 출고·입고·반품은 위 판단대로 막지 않는다.

## 도메인

### `CycleCount`

| 필드 | 설명 |
|------|------|
| `status` | `OPEN` / `SUBMITTED` / `APPROVED` / `REJECTED` |
| `memo` | 실사 사유·범위 메모(선택) |
| `createdBy`, `createdAt` | 세션을 연 사람 |
| `submittedBy`, `submittedAt` | 제출한 사람 |
| `approvedBy`, `approvedAt` | 승인한 사람 |
| `rejectedBy`, `rejectedAt`, `rejectReason` | 반려한 사람과 사유 |
| `items` | `CycleCountItem` 1:N (cascade ALL, orphanRemoval) |

### `CycleCountItem`

| 필드 | 설명 |
|------|------|
| `productId` | 대상 상품 |
| `bookQtyAtOpen` | 세션 생성 시점 장부 수량 — **표시 전용. 차이 계산에 쓰지 않는다.** |
| `countedQty` | 실물 수량. `null` = 미입력 |

`bookQtyAtOpen`은 상세 화면에서 *"세션 시작 72 → 승인 시점 70(실사 중 −2 이동)"* 을 보여주기 위한
증거다. 이 값으로 차이를 계산하면 위의 기준 시점 결정이 무너진다.

### 적용된 차이를 저장하지 않는 이유

품목에 `appliedDelta` 같은 필드를 두지 않는다. 원장이 정본이고, `reference = "COUNT#{세션id}"` 로
조회하면 품목별 `delta`·`beforeQty`·`afterQty`가 모두 나온다. 저장하면 같은 숫자의 정본이 둘이 된다.

차이가 0이라 원장 행이 없는 품목은 **"일치"** 로 표시한다. 그 품목의 승인 시점 장부 수량은
정의상 실물 수량과 같으므로 따로 저장할 필요가 없다.

## 승인 처리

```
for (item : session.items) {
    diff = item.countedQty - inventory(item.productId).onHandQty   // 승인 시점 재계산
    if (diff != 0)
        inventoryService.applyDelta(productId, diff, COUNT, "COUNT#" + sessionId, memo)
}
session.approve(actor)
```

- **`applyDelta` 재사용**이 핵심이다. 재고 증가 경로가 하나뿐이라, 실사로 재고가 늘면
  OMS 백오더 승격 통지(S3)가 자동으로 따라온다. 창고에 물건이 더 있었다는 사실은 입고와 같다.
- **전부 아니면 전무.** 한 품목이라도 실패하면 세션 전체가 롤백된다. `applyDelta`는 예약 수량
  미만으로 줄이는 조정을 거부하는데, 이때 앞 품목만 반영되면 "절반만 승인된 실사"가 남는다.
- 반려는 원장을 건드리지 않는다.

## 대상 선정과 겹침

세션을 열 때 상품을 직접 고른다. 전수 실사는 "전체 선택"이므로 모델 하나로 순환·전수를 모두 표현한다.

**같은 상품이 이미 열린 세션(`OPEN` 또는 `SUBMITTED`)에 있으면 새 세션 생성을 거부한다.**
승인 시점 재계산이라 두 세션이 각자 수렴하긴 하지만, 나중 세션의 실물 수량은 이미 낡은 값이라
"센 시점"과 "적용 시점"이 어긋난 조정이 남는다.

## 원장 행위자

```java
interface ActorProvider { String current(); }
```

`SecurityContextHolder`를 얇게 감싼 구현을 주입한다. 인증이 없거나 익명이면 `"system"`.

| 경로 | 값 |
|------|-----|
| 관리자 화면(입고·조정·반품 검수·실사 승인) | `operator` / `manager` |
| OMS 서버간 호출(출고) | `wms` |
| 기동 시드·백필 | `system` |

`InventoryTransaction`에 `actor`(nullable)를 추가하고, 기록 지점 두 곳(`InventoryService.applyDelta`,
`shipAll`)에서만 `ActorProvider`를 부른다. 호출부는 바뀌지 않는다.

**기존 행은 백필하지 않는다.** 과거에 누가 했는지는 알 수 없는 정보다. `type`을 `ADJUST`로 채웠던
지난 백필은 "조정이었음이 확실"해서 가능했지만, 행위자는 그런 근거가 없다. 화면에는 `—`로 표시한다.

## 권한

| 동작 | 권한 |
|------|------|
| 세션 생성 · 실물 입력 · 제출 | 인증(OPERATOR 이상) |
| 승인 · 반려 | **MANAGER** |

계수와 승인을 나누는 것이 실사의 기본 통제다 — 센 사람이 스스로 장부를 고치지 못한다.
수동 `ADJUST`는 긴급 경로로 그대로 둔다. 이제 원장에 행위자가 남으므로 두 경로의 성격이 분명히 갈린다.

| URL | 설명 | 권한 |
|-----|------|------|
| `/admin/cycle-counts` | 실사 목록 — 상태 필터, 진행률 | 인증 |
| `/admin/cycle-counts/new` | 대상 상품 선택 후 세션 생성 | 인증 |
| `/admin/cycle-counts/{id}` | 상세 — 장부·실물 입력·차이 미리보기, 제출/승인/반려 | 인증(승인·반려 버튼은 MANAGER) |

- 재고 이력 화면에 **행위자 열** 추가, 유형 필터에 **실사** 추가
- 대시보드에 **승인 대기 실사** 카드
- 상태는 한글로 표시(작성 중 / 승인 대기 / 승인 / 반려) — enum 원문 미노출
- 승인은 되돌릴 수 없으므로 확인창을 둔다(반품 검수와 같은 이유)

## 오류 처리

| 상황 | 처리 |
|------|------|
| 상태 전이 위반(예: `OPEN`을 승인) | `IllegalStateException` → flash |
| 미입력 품목이 있는데 제출 | `IllegalArgumentException` → flash, 상태 불변 |
| 대상 0개 · 없는 상품 · 음수 실물 수량 | `IllegalArgumentException` → flash |
| 겹치는 열린 세션 | `IllegalStateException` → flash |
| 승인 중 재고 제약 위반(예약분 미만) | `applyDelta`가 거부 → **세션 전체 롤백** → flash |
| DB 계층 예외 | 기존 `AdminDataAccessAdvice`(POST는 목록 복귀, GET은 503) |

## 마이그레이션

- `InventoryTransactionType`에 `COUNT` 추가 → **prod Postgres check 제약 갱신 필요**.
  `docs/wms-enum-schema-migration.md`의 절차를 그대로 따르고, 스크립트에 `COUNT`를 반영한다.
  (그 문서가 예고한 "다음 enum 추가"가 바로 이것이다.)
- `inventory_adjustment`에 `actor` 컬럼 추가 — nullable이라 `ddl-auto: update`가 생성한다.

## 비범위

위치·다중창고, 실사 대상 자동 추천(ABC 분석·회전율), 실사 스케줄링, 차이 금액 환산,
재고 연령(aging), 실사 중 대상 동결, 모바일·바코드 스캔 입력, 차이 임계값에 따른 승인 단계 분기,
과거 원장 행위자 백필.
