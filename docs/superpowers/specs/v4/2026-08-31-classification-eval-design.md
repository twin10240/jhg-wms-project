# 반품 사유 분류 품질 평가 — 설계

2026-08-31 · V4.0 후속

## 왜

V4.0을 병합했지만 **분류가 얼마나 맞는지 모른다.** 지금까지의 근거는 수동으로 넣어본 5건이 전부이고, 그것도 눈으로 보고 "그럴듯하다"고 판단한 것이다. 이 상태에서는 프롬프트를 고쳐도 나아졌는지 알 수 없다.

두 가지를 재려 한다.

1. **정확도** — 모델이 맞는 범주를 고르는가.
2. **처분 제안의 존재 이유** — `category`가 정해지면 `suggested_disposition`이 따라오는가. 따라온다면 그 필드는 모델에게 물을 것이 아니라 매핑 테이블로 충분하다.

두 번째는 정답이 필요 없다. 모델이 맞든 틀리든 **같은 범주에 항상 같은 처분이 붙는지**만 보면 되기 때문이다.

### 운영 데이터를 기다리지 않는 이유

"표본이 쌓이면 보자"는 느릴 뿐 아니라 나쁜 방법이다. 매핑을 깨뜨릴 케이스가 실제 반품에 우연히 섞여 들어오기를 기다리는 셈이기 때문이다. 5건에서 `REJECTED`가 한 번도 나오지 않은 것이 그 증거다. 평가셋은 그런 케이스를 **일부러 넣을 수 있다.**

## 무엇을 재고 무엇을 재지 않는가

| 값 | 다루는 방식 | 이유 |
|---|---|---|
| `category` | **정답과 대조해 채점** | 프롬프트에 정의가 명확해 사람이 라벨을 달 때 이견이 적다 |
| `suggested_disposition` | 정답 없이 **분포만 관찰** | "긁힘 있는 물건을 폐기할지"는 실물을 봐야 안다. 프롬프트도 그렇게 지시한다 |
| `confidence` | 정답 없이 **분포만 관찰** | 위와 같다. 다만 "흔들리는 케이스에서 LOW를 주는가"는 교차해 본다 |
| `evidence` | **평가하지 않음** | 좋은 인용의 정답을 정의할 수 없다 |

정답을 매길 수 없는 값에 점수를 매기면 점수가 의미를 잃는다. 그것이 이런 평가에서 가장 흔한 함정이다.

## 평가셋

`src/test/resources/eval/return-reasons.json` — 30건.

```json
{ "id": "damaged-01",
  "reason": "택배 박스가 찌그러져서 안에 컵이 깨졌어요",
  "expectedCategory": "DAMAGED",
  "note": "파손이 명시적. 기본 케이스" }
```

`note`는 장식이 아니다. 나중에 점수가 흔들렸을 때 **이 케이스가 왜 여기 있는지**를 알아야 판단할 수 있다. 라벨만 남으면 반년 뒤 해석이 불가능하다.

### 배분

| 범주 | 건수 |
|---|---|
| `DAMAGED` | 7 |
| `WRONG_ITEM` | 7 |
| `CHANGED_MIND` | 8 |
| `OTHER` | **8** |

`OTHER`에 가장 많이 배정한다. 실제 관측에서 **한 번도 나오지 않은 범주**이고, 프롬프트는 "애매하면 OTHER를 쓰고 confidence를 낮춰라"라고 지시하는데 모델이 따르지 않는 정황이 있다(`rmaId=452`, "음… 그냥 별로네요" → `OTHER`가 아니라 `CHANGED_MIND`+`LOW`). 가장 의심스러운 곳에 표본을 더 준다.

이것은 중립적 배분이 아니라 **가설을 겨냥한 배분**이다. 그래서 범주별 정확도를 전체 정확도와 함께 보고, 전체 정확도 하나만으로 판단하지 않는다.

### 매핑 탐침 케이스

30건 중 8건은 `category → disposition`이 갈릴 만한 사유를 겸한다.

- "몇 번 써봤는데 안 맞아서요" — 변심이지만 사용 흔적이 있다
- "긁힘이 있는데 쓰는 데는 문제없어요" — 파손이지만 재판매가 가능할 수 있다
- "포장만 뜯었어요" — 변심, 재입고가 자연스럽다

같은 범주 안에서 처분이 갈리면 매핑은 함수가 아니고, 그 필드는 모델에게 물을 값이다.

### 라벨의 권위

**초안은 Claude가 쓰고 사람이 검수한다.** 최종 권위는 사람에게 있다. 모델이 만든 라벨로 모델이 만든 프롬프트를 채점하면 순환이기 때문이다. 이 사실은 결과 문서에도 적는다 — 점수를 읽는 사람이 라벨의 출처를 알아야 한다.

## 반복 실행

**각 사유를 3회 분류한다.** 30건 × 3 = 90회, 약 148원.

1회로 충분하지 않은 이유: 30건에서 4건이 틀렸을 때 그것이 실력인지 흔들림인지 구분할 수 없다. 프롬프트를 고칠지 말지를 그 숫자로 결정하게 되는데 근거가 약하다.

3회는 **다수결 정확도**와 **흔들림**을 함께 준다. 3회 답이 갈린 케이스는 경계로 표시하고, 그 케이스들에서 모델이 실제로 `LOW`를 주는지 교차해 본다 — 그것이 `confidence`가 제 역할을 하는지 보는 방법이다.

비용은 판단 근거가 못 된다(50원과 148원의 차이).

## 구조

두 조각으로 나눈다.

### `EvalAggregator` — 순수 집계

다수결, 흔들림 판정, 범주별 정확도, 처분 매핑 집계, 토큰 합계. **API를 모른다.**

가짜 결과 목록으로 **오프라인 단위 테스트**를 붙인다. 집계가 틀리면 유료 실행 결과를 통째로 잘못 읽게 되므로, 이 부분은 공짜로 검증해야 한다. 이 테스트는 기본 `test`에 포함된다.

### `ClassificationEvalTest` — 실제 호출

`@Tag("eval")`. 실제 `ClaudeReturnReasonClassifier`를 직접 생성한다(스프링 컨텍스트가 필요 없다 — 생성자는 클라이언트와 `ObjectMapper`만 받는다).

- `ANTHROPIC_API_KEY`가 없으면 `Assumptions`로 **스킵**한다. 실패가 아니다.
- **병렬 5.** 90회를 순차로 돌리면 9분이다(회당 약 6초). 동시 5면 2분 안쪽이고 rate limit에도 여유가 있다.
- **점수로 실패하지 않는다.** 임계값을 두지 않는다. 실패 조건은 오직 "러너가 못 돌았다"이다. 비결정적 출력에 임계값을 걸면 언젠가 반드시 헛경보가 나고, 지금 목적은 회귀 게이트가 아니라 측정이다.

## 실행 분리 — CI가 과금하지 않는 것이 최우선

```groovy
tasks.named('test') {
    useJUnitPlatform { excludeTags 'eval' }
}

tasks.register('evalTest', Test) {
    useJUnitPlatform { includeTags 'eval' }
    testClassesDirs = sourceSets.test.output.classesDirs
    classpath = sourceSets.test.runtimeClasspath
    outputs.upToDateWhen { false }
}
```

CI는 `./gradlew build`를 돌리므로 `test`에서 제외하면 닿지 않는다. `outputs.upToDateWhen { false }`는 Gradle이 "변경 없음"으로 건너뛰지 않게 한다 — 이 태스크는 매번 실제로 돌아야 의미가 있다.

이 저장소는 지금까지 `@Tag`를 쓰지 않았다. 이것이 첫 태그다.

## 출력

러너는 `build/reports/classification-eval.md`에 쓴다. **커밋 대상 문서를 직접 덮어쓰지 않는다** — 수동으로 적어둔 해석이 재실행에 날아가면 안 된다. 결과를 `docs/wms-classification-eval.md`로 옮기는 것은 사람이 한다.

```
분류 품질 평가 — 2026-08-31 · claude-haiku-4-5-20251001 · 30건 × 3회

다수결 정확도    26/30 (86.7%)
흔들린 케이스     4건

범주별
  DAMAGED        7/7
  WRONG_ITEM     6/7   (1건 → OTHER)
  CHANGED_MIND   8/8
  OTHER          5/8   (3건 → CHANGED_MIND)

처분 매핑 (90회 관측)
  DAMAGED        → DISPOSED  21/21
  WRONG_ITEM     → RESTOCKED 18/18
  CHANGED_MIND   → RESTOCKED 31/33, REJECTED 2/33
  OTHER          → RESTOCKED 18/18

신뢰도 분포              HIGH 61 · MEDIUM 22 · LOW 7
흔들린 케이스의 신뢰도    LOW 5/12 · MEDIUM 6/12 · HIGH 1/12

누적 토큰        88,214 in / 3,684 out (약 148원)
```

(위 숫자는 형식을 보이기 위한 예시이며 실측이 아니다.)

**모델 스냅샷을 반드시 적는다.** `claude-haiku-4-5-20251001`에서 잰 점수는 그 버전의 점수지 영원한 점수가 아니다. 스냅샷 없는 숫자는 나중에 해석되지 않는다.

## 결과 문서

`docs/wms-classification-eval.md`. 회차별로 덧붙인다. 각 회차에 실행 날짜, 모델 스냅샷, 프롬프트 커밋 해시, 결과표, 그리고 **그 결과에서 무엇을 판단했는지**를 적는다. 마지막 항목이 핵심이다 — 숫자만 쌓이고 판단이 없으면 문서가 아니라 로그다.

## 하지 않는 것

- **임계값·게이트** — 비결정적 출력에 걸면 헛경보가 난다
- **이전 회차와 자동 비교** — 회차가 하나뿐인데 비교 인프라부터 지을 이유가 없다. 필요해지면 그때
- **CI 통합** — 과금과 비결정성 둘 다 CI에 맞지 않는다
- **`evidence` 품질 평가** — 정답을 정의할 수 없다
- **프롬프트 개선** — 이 작업은 재는 것까지다. 고치는 것은 잰 다음이다

## 성공 기준

이 작업이 끝났을 때 다음 세 질문에 숫자로 답할 수 있어야 한다.

1. 분류가 얼마나 맞는가 — 전체와 범주별로.
2. `suggested_disposition`은 `category`로 유도되는가, 아니면 모델에게 물을 값인가.
3. `confidence`는 흔들리는 케이스를 실제로 낮게 표시하는가.

점수가 좋든 나쁘든 이 작업은 성공이다. **재는 것이 목적이지 잘 나오는 것이 목적이 아니다.**
