# 반품 사유 자동 분류 — WMS V4.0 스펙

## 왜 이 기능인가

이 저장소의 첫 AI 기능이다. 고를 때 기준은 "무엇이 화려한가"가 아니라
**"틀려도 시스템이 틀린 답을 내지 않는가"** 였다.

반품 사유는 고객이 자유 텍스트로 쓴다(`RmaReturn.reason`). 검수자는 그걸 읽고 처분을 정하는데,
그 판단 자체는 사람이 물건을 봐야 한다. 그래서 분류는 **판단을 대신하지 않고 읽기를 돕는다.**

재고를 바꾸지도, 상태를 전이시키지도 않는다. 분류가 실패하거나 이상한 값을 내도
`RmaReturnItem.inspect()`의 검증 규칙은 그대로이고 검수는 지장 없이 진행된다.

## 경계 — AI에게 맡기는 것과 맡기지 않는 것

```
사유 텍스트 ──▶ [분류기] ──▶ 카테고리 · 근거 · 처분 제안 ──▶ 화면에 "참고"로 표시
                                                              │
재고 · 상태 · 검증 규칙 ──────────────────────────────────────┘ 영향 없음
```

| 맡긴다 | 맡기지 않는다 |
|--------|---------------|
| 자유 텍스트에서 사유 범주를 뽑는 일 | 승인 수량·처분의 **확정** |
| 판단 근거를 원문에서 인용하는 일 | 재고 반영, 상태 전이 |
| 처분을 **제안**하는 일 | 파손 정도 판정 (실물을 봐야 안다) |

검수 폼의 입력칸은 **여전히 비어 있다.** V2.1에서 "되돌릴 수 없는 확정에 기본값을 두지 않는다"를
세웠고, AI 제안이 그 원칙의 예외가 되지 않는다. 제안은 화면에 별도 영역으로 표시할 뿐
입력칸을 채우지 않는다.

## 데이터 모델

분류는 `RmaReturn`의 필드가 아니라 **별도 엔티티**로 둔다.

```java
@Entity
@Table(name = "return_classification")
class ReturnClassification {
    Long id;
    Long rmaReturnId;                      // 1:1, UNIQUE
    ReturnCategory category;               // DAMAGED / WRONG_ITEM / CHANGED_MIND / OTHER
    Confidence confidence;                 // HIGH / MEDIUM / LOW
    String evidence;                       // 사유 원문에서 인용한 근거
    RmaDisposition suggestedDisposition;   // 기존 enum 재사용
    String model;                          // 예: claude-haiku-4-5
    int inputTokens;
    int outputTokens;
    Instant classifiedAt;
}
```

**왜 별도 엔티티인가.** 분류는 RMA의 상태가 아니라 참고 정보다. 도메인에 섞으면 "이 필드가
업무 규칙인가 힌트인가"가 흐려진다. 또 없을 수 있는 값 넷이 늘면 `RmaReturn`이 그만큼 지저분해진다.

**`suggestedDisposition`은 기존 `RmaDisposition`을 재사용한다.** 새 enum을 만들면 나중에 실제
검수 결과와 대조할 때 매핑이 필요해진다. 같은 타입이어야 그냥 비교된다.

**정답 대조를 위한 준비**: 제안(`suggestedDisposition`)과 실제 결과(`RmaReturnItem.disposition`)를
둘 다 저장해두면, 데이터가 쌓인 뒤 정확도를 계산할 수 있다. 이번 범위는 저장까지다.

## 호출 경계

```java
interface ReturnReasonClassifier {
    Optional<Classification> classify(String reason);   // 실패는 Optional.empty()
}
```

인터페이스를 두는 이유는 둘이다. 서비스가 특정 SDK에 묶이지 않고, **테스트가 API를 호출하지
않아도 되게** 하기 위해서다.

### 언제 부르는가

`RmaService.createReturn`의 **트랜잭션 커밋 후**에 시도한다. `OmsReturnStatusNotifier`가 이미
쓰는 `afterCommit` 패턴과 같은 모양이며, 새 패턴을 만들지 않는다.

```
POST /api/returns
  └─ 접수 저장 → 커밋 → 201 응답 (OMS는 여기서 끝)
        └─ afterCommit: 분류 시도
              성공 → ReturnClassification 저장
              실패 → warn 로그, 분류 없음
```

이 배치가 중요한 이유는 `POST /api/returns`가 **OMS가 부르는 API**이기 때문이다. 트랜잭션 안에서
외부 LLM을 부르면 OMS 응답이 LLM 지연에 묶이고, API 장애가 반품 접수를 막는다.

### 실패했을 때

| 상황 | 처리 |
|------|------|
| 타임아웃 · 연결 실패 | `empty` → 분류 없음, `warn` 로그 |
| 스키마 위반 (enum 이탈, 필드 누락) | `empty` → 저장하지 않음 |
| `reason`이 비었거나 공백 | **호출 자체를 하지 않음** (비용 낭비) |
| API 키 미설정 | 기동은 정상, 분류만 비활성 |

어느 경우든 접수 트랜잭션은 이미 커밋됐으므로 영향이 없다. 화면은 "분류 없음"으로 보인다.

**재시도 스윕은 두지 않는다.** 분류는 참고 정보라 빠져도 업무가 막히지 않는데, 스케줄러와
중복 방지 코드가 함께 늘어난다. 빠진 건이 실제로 불편해지면 그때 추가한다.
(OMS 통지는 스윕이 있다 — 그쪽은 빠지면 두 시스템 상태가 갈리기 때문이고, 성격이 다르다.)

**API 키를 prod fail-fast 대상으로 두지 않는다.** `wms.basic`·`oms.callback`은 없으면 통신이
전면 실패하므로 기동을 막지만, 분류는 없어도 창고 업무가 돌아간다.

## 화면

반품 상세(`/admin/returns/{id}`)의 사유 아래에 참고 영역을 둔다.

```
사유: "받았는데 모서리가 깨져 있어요"

  분류 제안   파손 · 신뢰도 높음
  근거        "모서리가 깨져 있어요"
  처분 제안   폐기
  참고용입니다. 확정은 직접 입력하세요.

승인 수량 [    ]   처분 [선택하세요 ▾]     ← 여전히 비어 있음
```

- 분류가 없으면 이 영역을 통째로 렌더하지 않는다(빈 껍데기를 두지 않는다)
- enum 원문을 노출하지 않는다 — 한글 라벨(파손/오배송/변심/기타, 높음/보통/낮음)
- 제안과 입력칸을 **시각적으로 분리**한다. 제안이 입력의 기본값처럼 보이면 안 된다

## 프롬프트

`src/main/resources/prompts/return-classification.txt`에 둔다. 코드 상수로 두면 프롬프트 변경이
diff에서 안 보이고, 프롬프트는 코드만큼 자주 바뀐다.

출력은 구조화 출력(JSON 스키마)으로 강제한다. 자유 텍스트를 파싱하지 않는다 —
비결정적 응답을 결정적 경계 안에 가두는 것이 이 기능의 핵심이다.

## 비용 관측

`inputTokens`·`outputTokens`를 엔티티에 저장하고 로그에도 남긴다.
"AI 기능을 붙였는데 얼마 드는지 모른다"를 피하기 위해서다.

기준 감각: Haiku(`$1/$5` per 1M) 기준 분류 1건이 입력 약 400 · 출력 약 120 토큰이면
**건당 약 $0.001(1.4원)**, 반품 100건이면 약 140원이다.

## 테스트

**자동 테스트에서 실제 API를 호출하지 않는다.** 현재 325건이 외부 의존 없이 도는 성질을 지킨다.

| 계층 | 무엇을 검증하나 |
|------|-----------------|
| 서비스 | 가짜 분류기 주입 — 성공 시 저장, 실패(`empty`) 시 미저장·접수는 정상, 빈 사유면 호출 안 함 |
| 어댑터 | **고정 JSON 응답**으로 파싱 검증 — 정상, enum 이탈, 필드 누락, 잘린 JSON |
| 화면 | 분류 있음/없음 렌더, 한글 라벨, **입력칸이 여전히 비어 있음** |
| 수동 | 실제 API 호출 스모크 1회 — 결과와 토큰 수를 검증 기록에 남김 |

어댑터 테스트가 고정 JSON을 쓰는 이유는 비용·불안정 때문만이 아니다. **모델이 스키마를 어겼을 때
우리 코드가 어떻게 행동하는지**가 검증 대상이고, 그건 실제 호출로는 재현할 수 없다.

## 비범위

정확도 측정(eval)과 리포트, 재분류·수동 재시도 UI, 분류 결과 기반 자동 처분, 다국어,
사유 외 필드(사진·주문 이력) 활용, 프롬프트 A/B 비교, 배치 API, 캐싱.

정확도 측정을 뺀 이유는 현재 RMA가 11건이라 숫자가 의미를 갖지 못하기 때문이다.
제안과 실제 결과를 함께 저장해두는 것까지가 이번 범위이고, 데이터가 쌓이면 그때 계산한다.
