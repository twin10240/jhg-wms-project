# 발주 근거 패널 설계

날짜: 2026-09-05

## 배경

"발주 메모를 AI로 읽어 상품별 패턴·소모량을 추측한다"는 아이디어에서 출발했다. 점검 결과 전제가 둘 다 서지 않았다.

1. **사람이 쓴 발주 메모가 0건이다.** `purchase_order` 1행이 있고 그 메모는 `ReplenishmentRequestService.approve()`가 조립한 `"OMS 보충 요청 #1 - ..."` 문자열이다. 분류할 모수가 없다.
2. **소모량은 메모가 아니라 원장에 있다.** `inventory_adjustment`에 SHIP 341건 / 17개 상품(2026-08-27~09-05). 상품·기간으로 합치면 나오는 값이라 추론이 아니라 산술이다. 여기에 LLM을 쓰면 이미 정확한 숫자를 확률적으로 다시 만드는 셈이 되고, 틀려도 알아채기 어렵다.

그래서 순서를 뒤집는다. **먼저 발주 시점에 원장 근거를 보여준다.** 사람이 그 근거를 보고 메모를 쓰기 시작하면, 그때 메모 범주화(`ClaudeReturnReasonClassifier` 틀 복제)가 의미를 갖는다. 이 스펙은 1단계만 다룬다.

## 범위

발주 화면(`/admin/purchase-orders`) 발주 폼 **위**에 상품별 근거 표를 하나 띄운다. 서버사이드 렌더 한 번. 새 엔드포인트도 JS도 없다.

AI는 이 단계에 없다.

## 계산

`PurchaseOrderAdviceService.advise(today)` 가 상품당 한 행을 낸다.

| 값 | 출처 |
|---|---|
| 창 안 SHIP 합계 | `InventoryTransactionRepository.sumDeltaByProductAndTypeInPeriod()` — **이미 있음**, SHIP만 거른다 |
| 표본 일수 | 상품별 원장 최초 시각 — **새 쿼리 1개** |
| 일평균 소모량 | 합계 ÷ 표본 일수 |
| onHand / reserved / available | `InventoryService.findAllRows()` — 이미 있음 |
| 소진 예상일 | available ÷ 일평균 |
| 직전 발주 (발주번호·발주일·수량·입고일·리드타임·상태) | `PurchaseOrderService.findAllWithItems()` — 이미 있음, 메모리 그룹핑 |

## 창(window)과 표본 일수

기본 창은 **30일**(오늘 포함, 반개구간 `[today-29일 00:00, today+1일 00:00)`). 원장 조회 경계는 기존 `InventoryLedgerAnalyticsService`와 같은 `LocalDateTime` 규약을 따른다 — `InventoryTransaction.createdAt`이 `LocalDateTime`이라 `ReservationAnalyticsService`의 `Asia/Seoul` 변환은 여기 필요 없다.

**일평균의 분모는 창 길이가 아니라 그 상품의 원장이 실제로 존재한 일수다.**

```
표본 시작 = max(창 시작, 그 상품 원장의 최초 날짜)
표본 일수 = 오늘 - 표본 시작 + 1
```

지금 데이터가 정확히 이 경우다. 원장이 2026-08-27부터라 10일치인데 30으로 나누면 일평균이 실제의 1/3로 나오고 **소진 예상일이 3배 길어진다.** 재고가 버틸 거라고 잘못 말하는 쪽이라 조용히 틀리면 안 된다. 표본 일수는 나눗셈에 쓰고 화면에도 행마다 적는다.

**일평균이 0이면 소진 예상일은 `null`이다.** `0일`이 아니다 — 반품·체류 도구가 `count: 0`에 `null`을 내는 것과 같은 이유로, 잴 것이 없는 것과 오늘 소진되는 것은 다르다. 원장이 아예 없는 상품(표본 일수 0)도 같다.

정렬은 소진 예상일 오름차순, `null`은 맨 뒤, 동률은 상품 ID.

## 화면

발주 폼 위 표 하나. 열: 상품 / 최근 출고(표본 일수) / 일평균 / 가용 / 소진 예상 / 직전 발주.

- 표본 일수는 열 머리에 한 번이 아니라 **행마다** 적는다. 상품별로 다르다.
- 소진 예상이 없는 행은 `—`.
- `ai-hint` 계열 스타일을 쓰되 **"참고" 태그는 달지 않는다.** AI 출력이 아니라 산술이라, 같은 표시를 쓰면 신뢰도 표기가 흐려진다.
- 원장이 한 행도 없으면 표를 통째로 렌더하지 않는다 — `returndetail.html`이 분류 없을 때 하는 것과 같다(빈 껍데기를 두지 않는다).

## 검증

`PurchaseOrderAdviceServiceTest` (`@DataJpaTest`, 기존 분석 서비스 테스트와 같은 형태):

- 일평균 0 → 소진 예상 `null` (0일로 읽지 않는다)
- 표본 일수가 창보다 짧으면 **짧은 쪽으로** 나눈다 (10일치를 30으로 나누는 사고 차단)
- 정렬에서 `null`이 맨 뒤
- 원장이 비면 빈 목록

## 안 하는 것

- **메모 범주화(2단계).** 분류할 메모가 0건이라 지금 만들면 빈 화면이다. 이 패널이 들어간 뒤에 붙인다.
- **권장 발주량.** 목표 재고일수를 사람이 대야 하는데, 그 값이 수량칸 기본값에 숨으면 "제안을 기본값으로 두지 않는다"는 반품 분류의 원칙이 무너진다.
- **금액 환산.** WMS에는 수량뿐이다.
