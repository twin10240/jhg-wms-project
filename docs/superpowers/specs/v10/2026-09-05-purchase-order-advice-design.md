# 발주 근거 패널 설계

날짜: 2026-09-05

## 배경

"발주 메모를 AI로 읽어 상품별 패턴·소모량을 추측한다"는 아이디어에서 출발했다. 점검 결과 전제가 둘 다 서지 않았다.

1. **사람이 쓴 발주 메모가 0건이다.** `purchase_order` 1행이 있고 그 메모는 `ReplenishmentRequestService.approve()`가 조립한 `"OMS 보충 요청 #1 - ..."` 문자열이다. 분류할 모수가 없다.
2. **소모량은 메모가 아니라 원장에 있다.** `inventory_adjustment`에 SHIP 341건 / 17개 상품(2026-08-27~09-05). 상품·기간으로 합치면 나오는 값이라 추론이 아니라 산술이다. 여기에 LLM을 쓰면 이미 정확한 숫자를 확률적으로 다시 만드는 셈이 되고, 틀려도 알아채기 어렵다.

그래서 순서를 뒤집는다. **먼저 발주 시점에 원장 근거를 보여준다.** 사람이 그 근거를 보고 메모를 쓰기 시작하면, 그때 메모 범주화(`ClaudeReturnReasonClassifier` 틀 복제)가 의미를 갖는다. 이 스펙은 1단계만 다룬다.

> **개정 있음(2026-09-09).** 실제 구현은 같은 브랜치에서 2단계(메모 범주화)까지 실었다. 이 문서 맨 아래 [개정 이력](#개정-이력-2026-09-09)을 먼저 읽을 것 — 여기까지만 읽으면 "이 작업에 AI가 없다"고 잘못 읽힌다.

## 범위

발주 화면(`/admin/purchase-orders`) 발주 폼 **위**에 상품별 근거 표를 하나 띄운다. 서버사이드 렌더 한 번. 새 엔드포인트도 JS도 없다.

~~AI는 이 단계에 없다.~~ → 근거 패널 자체에는 지금도 AI가 없다(산술이다). 다만 같은 브랜치가 발주 **메모 분류**를 함께 실었다 — 개정 이력 참조.

## 계산

`PurchaseOrderAdviceService.advise(today, rows, purchaseOrders)` 가 상품당 한 행을 낸다. (시그니처는 2026-09-09에 바뀌었다 — 개정 이력 R2 참조.)

| 값 | 출처 |
|---|---|
| 창 안 SHIP 합계 | `InventoryTransactionRepository.sumDeltaByProductAndTypeInPeriod()` — **이미 있음**, SHIP만 거른다 |
| 표본 일수 | 상품별 원장 최초 시각 — **새 쿼리 1개** |
| 일평균 소모량 | 합계 ÷ 표본 일수 |
| onHand / reserved / available | `InventoryService.findAllRows()` — 이미 있음 |
| 소진 예상일 | available ÷ 일평균 |
| 직전 발주 (발주번호·발주일·수량·입고일·리드타임·상태) | `PurchaseOrderService.findAllWithItems()` — 이미 있음, 메모리 그룹핑. **비교 기준은 날짜가 아니라 `createdAt` 시각**(개정 이력 R1 참조) |

## 창(window)과 표본 일수

기본 창은 **30일**(오늘 포함, 반개구간 `[today-29일 00:00, today+1일 00:00)`). 원장 조회 경계는 기존 `InventoryLedgerAnalyticsService`와 같은 `LocalDateTime` 규약을 따른다 — `InventoryTransaction.createdAt`이 `LocalDateTime`이라 `ReservationAnalyticsService`의 `Asia/Seoul` 변환은 여기 필요 없다.

**일평균의 분모는 창 길이가 아니라 그 상품의 원장이 실제로 존재한 일수다.**

```
표본 시작 = max(창 시작, 그 상품 원장의 최초 날짜)
표본 일수 = 오늘 - 표본 시작 + 1
```

지금 데이터가 정확히 이 경우다. 원장이 2026-08-27부터라 10일치인데 30으로 나누면 일평균이 실제의 1/3로 나오고 **소진 예상일이 3배 길어진다.** 재고가 버틸 거라고 잘못 말하는 쪽이라 조용히 틀리면 안 된다. 표본 일수는 나눗셈에 쓰고 화면에도 행마다 적는다.

**일평균이 0이면 소진 예상일은 `null`이다.** `0일`이 아니다 — 반품·체류 도구가 `count: 0`에 `null`을 내는 것과 같은 이유로, 잴 것이 없는 것과 오늘 소진되는 것은 다르다. 원장이 아예 없는 상품(표본 일수 0)도 같다.

정렬은 소진 예상일 오름차순, `null`은 맨 뒤, 동률은 상품 ID.

## 화면

발주 폼 위 표 하나. 열: 상품 / 최근 출고(표본 일수) / 일평균 / 가용 / 소진 예상 / 직전 발주.

- 표본 일수는 열 머리에 한 번이 아니라 **행마다** 적는다. 상품별로 다르다.
- 소진 예상이 없는 행은 `—`.
- `ai-hint` 계열 스타일을 쓰되 **"참고" 태그는 달지 않는다.** AI 출력이 아니라 산술이라, 같은 표시를 쓰면 신뢰도 표기가 흐려진다.
- 원장이 한 행도 없으면 표를 통째로 렌더하지 않는다 — `returndetail.html`이 분류 없을 때 하는 것과 같다(빈 껍데기를 두지 않는다).

## 검증

`PurchaseOrderAdviceServiceTest` (`@DataJpaTest`, 기존 분석 서비스 테스트와 같은 형태):

- 일평균 0 → 소진 예상 `null` (0일로 읽지 않는다)
- 표본 일수가 창보다 짧으면 **짧은 쪽으로** 나눈다 (10일치를 30으로 나누는 사고 차단)
- 정렬에서 `null`이 맨 뒤
- 원장이 비면 빈 목록

## 안 하는 것

- **메모 범주화(2단계).** 분류할 메모가 0건이라 지금 만들면 빈 화면이다. 이 패널이 들어간 뒤에 붙인다.
- **권장 발주량.** 목표 재고일수를 사람이 대야 하는데, 그 값이 수량칸 기본값에 숨으면 "제안을 기본값으로 두지 않는다"는 반품 분류의 원칙이 무너진다.
- **금액 환산.** WMS에는 수량뿐이다.

## 개정 이력 (2026-09-09)

### 1. 2단계(메모 범주화)가 같은 브랜치에 들어갔다 — "안 하는 것"에서 빠진다

원래 사유는 "분류할 메모가 0건이라 지금 만들면 빈 화면"이었다. 브랜치가 그 전제를 **시드로 없앴고**
(`docs/seed-purchase-order-memo-demo.sh` — 폼 POST로 발주 메모 30건), 그래서 같은 브랜치에서
2단계까지 실었다. 실제로 들어간 것:

| 것 | 클래스 |
|---|---|
| 발주 메모 분류 서비스 | `PurchaseOrderMemoClassificationService` |
| 커밋 후 비동기 트리거 | `PurchaseOrderMemoClassificationTrigger` (OMS 보충 경로는 링크로 걸러 제외) |
| 응답 파서 | `PurchaseOrderMemoJsonParser` (근거 500자 절단, enum 미스·잘림 방어) |
| 저장 | `purchase_order_memo_classification` (`existsByPurchaseOrderId` 멱등) |
| 화면 | 발주 상세의 "메모 분류(참고) · 범주 · 신뢰도 · 근거" 블록 |

원칙은 반품 분류와 같다 — **참고 정보이고 발주 내용에 영향을 주지 않는다.** 화면에도 그렇게 적혀 있다.
근거 패널 쪽은 여전히 AI가 없다(산술). 한 화면에 산술과 추론이 같이 있으므로 표시를 구분한다:
근거 패널은 "참고" 태그를 달지 않고, 메모 분류는 단다.

### 2. R1 — "직전 발주"의 비교 기준을 날짜에서 시각으로 올렸다

원래 구현은 `createdAt.toLocalDate()`로 **일 단위** 비교라 같은 날 발주 둘이 동률이었고, 동률의 승자가
`findAllWithItems()`의 정렬(**열린 것 먼저·종료된 것 뒤** — 목록 화면용)에 좌우됐다. 그래서 같은 날
발주 #11(입고 완료)과 #12(미입고)가 있으면 닫힌 #11이 #12를 덮고, 패널이 "직전 발주 입고 완료"라
말하며 **아직 안 들어온 발주를 감췄다.** 당일 발주·당일 입고는 이 시스템 데이터의 실제 모습이다.

고침은 비교 함수 교체에서 멈추지 않았다 — **순회 자체를 `createdAt`(동률 시 id) 오래된 순으로 다시
정렬**한다. 비교만 고치면 동률 처리가 여전히 표현 계층 정렬에 의존해, 목록 정렬을 누가 바꾸면 이
패널의 뜻이 조용히 바뀐다.

### 3. R2 — 재고 행·발주 전건은 호출자가 넘긴다

`advise()`가 `findAllRows()`·`findAllWithItems()`를 스스로 부르면, 같은 핸들러가 목록을 그리려고 이미
부른 쿼리가 한 번 더 나간다(컨트롤러는 트랜잭션이 아니라 1차 캐시에 안 걸린다). 시그니처를
`advise(today, rows, purchaseOrders)`로 바꿔 넘겨받는다. 발주는 **상태 필터를 걸기 전 전건**이어야
한다 — 필터된 목록을 넘기면 "직전 발주"가 보고 있는 탭에 따라 달라진다.

부수 효과로 이 서비스의 `InventoryService`·`PurchaseOrderService` 의존이 사라지고 생성자가
원장 저장소 하나가 됐다.

### 4. 넣지 않기로 한 것 — `findFirstRecordedAtByProduct()`의 창 필터

리뷰가 "MIN 쿼리에 `WHERE t.createdAt >= :from`을 넣어 전체 스캔을 막자"고 했으나 **거부했다.**
이 값이 답하는 질문은 "이 상품 원장이 **언제 시작했나**"이고 `max(창 시작, 최초 기록일)`로 쓰인다.
창으로 자르면 MIN이 "창 안의 첫 거래일"이 되어 `max()`가 무력화되고,

- 창 앞부분이 조용한 오래된 상품은 분모가 줄어 **일평균이 부풀고 소진 예상일이 짧아진다** —
  이 스펙이 막으려던 사고("10일치를 30으로 나눠 3배 길어짐")의 **반대 방향으로** 틀린다.
- 창 내내 조용한 상품은 목록에서 빠지고, 창 전체가 조용하면 "원장이 한 행도 없음" 가드가 걸려
  **패널이 통째로 사라진다.**

전체 스캔이라는 사실은 맞으므로 저장소 쿼리에 `ponytail:` 주석으로 남기고 업그레이드 경로를
적었다: `(product_id, created_at)` 인덱스 → 그래도 모자라면 `Inventory`에 첫 기록일 컬럼.
