# 발주 브리핑 생성과 그 평가 설계

날짜: 2026-09-10

## 배경

지금 이 저장소의 AI는 전부 **분류**다. 반품 사유(V4.0)도 발주 메모(V10.0)도 정해진 범주 중
하나를 고르고, 평가는 사람이 검수한 정답 라벨에 다수결을 맞춰 채점한다.

**생성은 한 번도 안 했다.** 생성물은 정답 라벨이 없어서 지금 하네스로는 채점 자체가 성립하지
않는다. 이 스펙의 목적은 기능 하나를 더 붙이는 것이 아니라 **정답이 없는 출력을 어떻게 재는가**를
이 저장소 안에서 실측 가능한 형태로 세우는 것이다.

발주 화면을 고른 이유는 **채점의 반이 기계적으로 가능하기 때문**이다. 근거 패널이 이미 정확한
숫자를 내고 있으므로, 생성문에 나온 숫자가 그 값에 있는지 대조하면 환각을 모델 없이 잡을 수 있다.
judge가 못 잡는 것과 잡는 것을 가르는 실습을 여기서 할 수 있다.

## 이 설계가 시험대에 올리는 기존 원칙

`PurchaseOrderAdviceService`의 클래스 주석은 이렇게 선언한다 —

> AI가 없다. 상품별 소모량은 원장 SHIP 델타의 합이라 산술이지 추론이 아니다 —
> 이미 정확한 숫자를 모델에 다시 만들게 하면 틀려도 알아채지 못한다.

브리핑은 이 원칙과 정면으로 부딪친다. 모델에게 문단을 쓰게 하면 숫자를 문장 안에 다시 쓰기
때문이다. **그래도 그렇게 만든다** — 다만 추측으로 두지 않고 **환각률을 재고 나서** 구조를 정한다.

- 환각이 거의 없으면 → 지금 형태를 유지하고, "쟀더니 안 나더라"가 근거로 남는다
- 환각이 유의하면 → 모델이 숫자를 못 쓰게 구조화 출력으로 바꾸고, 그 결정에 실측치가 붙는다

이 순서는 반품 평가에서 이미 쓴 것이다(처분 매핑 테이블 대체안을 추측이 아니라 처분 분포를 재서
기각했다). **원칙을 지키는 방법이 원칙을 시험하지 않는 것은 아니다.**

## 범위

발주 화면(`/admin/purchase-orders`)에 버튼 하나. 누르면 근거 패널 상위 5개를 읽고 문단 하나를
생성해 보여준다. 그리고 그 생성물을 채점하는 평가 하네스.

**범위 밖**: 자동 생성(화면 진입·배치), 브리핑이 발주 내용에 영향을 주는 것, 상품 추천 로직.
브리핑은 기존 두 AI 기능과 같이 **참고 표시 전용**이다.

**두 단계로 나눠 실는다.** 1부(기능)가 없으면 2부(평가)가 잴 것이 없으므로 순서는 고정이다.
다만 **각 단계를 따로 검증하고 따로 원장에 적는다** — V10.0은 근거 패널과 메모 분류를 한
브랜치에 실었다가 리뷰·실기동 기록이 그 구간에만 비었다(원장 "미검증" 절). 같은 실수를
반복하지 않는다.

# 1부 — 기능

## 엔드포인트

`POST /admin/purchase-orders/briefing` → 생성 후 `/admin/purchase-orders`로 리다이렉트.
화면은 저장된 마지막 브리핑을 렌더한다. 새 JS 없음, 폼 POST 하나(`receive`·`cancel`과 같은 모양).

**기존 두 분류와 달리 동기다.** 반품·메모 분류는 커밋 후 별도 스레드로 던지고 사용자는 기다리지
않는다. 브리핑은 사용자가 버튼을 누르고 결과를 기다리는 **읽기 시점**이라 비동기 트리거 패턴을
쓸 수 없다. 여기서 따라오는 것들:

- 타임아웃: `wms.ai.timeout` 20초는 문단 생성에 빠듯하다 → 브리핑 전용 값을 둔다
- `max-tokens`: 1024는 짧은 JSON 기준이다 → 브리핑 전용 값을 둔다
- 실패: flash 에러만 띄우고 화면은 그대로. **브리핑이 없어도 발주 업무는 돈다**

`ANTHROPIC_API_KEY`가 없으면 버튼을 렌더하지 않는다(기존 "키 없으면 분류만 비활성"과 같은 취급).

## 입력

근거 패널의 **소진 예상 오름차순 상위 5개**. 전체를 넣으면 토큰이 커지고 브리핑도 "다 중요하다"가
되어 쓸모가 없어진다. 5는 근거 없는 값이므로 상수로 빼고 `ponytail:` 주석으로 그 사실을 남긴다.

컨트롤러가 이미 조회해 둔 `advice`를 넘겨받는다 — 서비스가 다시 부르면 같은 쿼리가 두 번 나간다
(V10.0에서 이미 겪은 문제, 근거 패널 스펙 R2 참조).

## 저장 — `purchase_order_briefing`

`PurchaseOrderMemoClassification`과 같은 이유로 도메인에서 떼어낸 별도 테이블이다. 브리핑은
발주의 상태가 아니라 참고 정보이고, 도메인에 섞으면 업무 규칙인지 힌트인지 흐려진다.

| 컬럼 | |
|---|---|
| `body` | 생성된 문단 |
| **`input_snapshot`** | **그때 모델에게 준 패널 값 (JSON)** |
| `model` · `input_tokens` · `output_tokens` · `created_at` | 기존 분류 테이블과 동일 |

**`input_snapshot`이 이 설계의 핵심이다.** 두 가지 이유로 없으면 안 된다:

1. **재고는 계속 변한다.** 브리핑을 나중에 열면 화면의 패널 값은 이미 다른 값이다. 스냅샷이
   없으면 "이 문장의 숫자가 맞았나"를 영영 판정할 수 없다.
2. **숫자 대조 채점기가 이것을 먹는다.** 채점의 근거 집합이 곧 스냅샷이다. 없으면 평가가
   성립하지 않는다.

## 프롬프트

`src/main/resources/prompts/purchase-order-briefing.txt`. 요구할 것:

- 상위 5개 중 **지금 발주할 것**과 그 이유를 쓴다
- **숫자는 준 값만 쓴다. 계산하지 않는다** — 이 문장이 있어야 파생값 사용이 오탐이 아니라
  진짜 위반이 된다(채점기 설계와 직결된다)
- 패널에 없는 사실을 지어내지 않는다(거래처 사정·시즌 등은 패널에 없다)
- 길이 상한을 준다

# 2부 — 평가

## 채점기 1: 사실성 (기계적, 모델 호출 없음)

생성문에서 숫자를 전부 뽑아 **스냅샷의 값 집합과 대조**한다.

```
근거 집합 = 스냅샷의 모든 수치
  (출고량 · 표본일수 · 일평균 · 가용 · 소진예상 · 직전 발주 번호/수량/날짜)
지표 ① 근거 없는 숫자 / 전체 숫자
지표 ② 환각이 1건이라도 있는 브리핑 / 전체 브리핑
```

지표 ②가 실무적으로 더 중요하다 — 문단 하나에 틀린 숫자 하나면 그 문단은 못 쓴다.

**반올림은 허용한다.** 일평균 3.23을 "3.2개"로 쓰는 것은 정상이다. 소수 1자리 반올림 일치까지
인정한다. 상품 ID·발주 번호는 정확히 일치해야 한다.

**오탐이 이 채점기의 진짜 설계 문제다.** "상위 5개", "최근 30일" 같은 메타 숫자는 스냅샷에
없지만 환각이 아니다. 화이트리스트로 빼야 하는데, **화이트리스트를 넓히면 진짜 환각도 같이
통과한다.** 이 균형을 못 잡으면 나온 점수를 믿을 수 없다. 실제로 돌려 보며 조정한다.

## 채점기 2: 유용성 (LLM-as-judge)

정답이 없으므로 모델에게 묻는다. 설계 선택 둘:

**점수(1~5)가 아니라 체크리스트 예/아니오.** 점수는 회차마다 흔들려 "3.4 → 3.7"이 개선인지
잡음인지 가릴 수 없다. 예/아니오면 기존 하네스의 3회 다수결이 그대로 적용된다.

**judge에게는 기계가 못 재는 것만 남긴다.** 처음 항목을 적으면 다섯 개쯤 나오는데 절반은
judge의 일이 아니다:

| 항목 | 누가 재나 |
|---|---|
| 가장 급한 상품(소진 예상 최소)을 언급했는가 | 기계 — judge에게 묻지 않는다 |
| 숫자가 정확한가 | 채점기 1이 이미 한다 |
| 각 언급에 왜 급한지 근거가 붙었는가 | judge |
| 패널에 없는 **사실**을 지어내지 않았는가(숫자 아닌 주장) | judge |
| 담당자가 바로 행동할 만큼 구체적인가 | judge |

judge는 흔들리고 비싸다. 기계가 확정적으로 답할 수 있는 것을 judge에게 맡기면 **비용을 더 내고
답을 덜 믿게 된다.**

## judge를 어떻게 믿는가

judge도 모델이므로 채점이 맞는지 모르는 채로 쓰면 의미가 없다. 두 가지로 검증한다.

**① 네거티브 케이스 — 정답을 아는 유일한 케이스다.** 좋은 브리핑을 일부러 망가뜨린 버전을
평가셋에 넣는다: 숫자를 틀리게 바꾼 것, 근거 문장을 뺀 것, 관계없는 상품을 넣은 것.
**judge가 이것을 떨어뜨리지 못하면 judge가 고장난 것이고, 그때 유용성 점수는 읽을 가치가 없다.**

**② 자기편향 관측.** 생성과 채점을 같은 `claude-haiku-4-5`로 하면 자기 출력에 후해질 수
있다(self-preference). 다른 계열로도 채점해 점수가 갈리는지 본다. 갈리면 그 자체가 관측 결과다.

**네거티브 케이스는 생성을 건너뛴다.** 평가셋에 브리핑 **본문을 직접 넣는다** — 모델에게
"망가진 브리핑을 써라"라고 시키면 무엇이 망가졌는지를 모델이 정하게 되고, 그러면 judge를
같은 모델의 판단으로 검증하는 순환이 된다. 사람이 손으로 망가뜨린 본문이라야 정답을 안다.

그래서 평가셋 케이스는 두 종류다:

| 종류 | 입력 | 생성 | 채점 |
|---|---|---|---|
| 정상 | 스냅샷만 | 한다 | 사실성 + judge |
| 네거티브 | 스냅샷 + **본문** + 떨어져야 할 항목 | **안 한다** | judge만 |

**크기: 정상 8건 + 네거티브 4건.** 정상 8건은 서로 다른 재고 모양이어야 한다(소진 임박이 여럿,
하나도 없음, 일평균 0이 섞임, 직전 발주가 취소됨 등) — 같은 모양을 여덟 번 재면 표본이 하나다.
네거티브 4건은 judge 항목 셋에 하나씩 + 숫자를 틀리게 바꾼 것 하나로, 항목마다 최소 한 번은
"떨어뜨려야 하는데 떨어뜨렸는가"가 확인된다.

## 리포트

두 채점의 집계 축이 다르다(비율 vs 항목별 통과율). **억지로 한 숫자로 합치지 않는다** —
"종합 4.2" 같은 값을 만들면 어느 쪽이 나빠서 떨어졌는지 읽을 수 없다.

```
## 네거티브 케이스   judge가 떨어뜨렸는가   ← 여기가 통과 못 하면 아래를 믿지 않는다
## 사실성           근거 없는 숫자 x/y · 환각 있는 브리핑 n/N
## 유용성           항목별 통과 / 흔들림
```

네거티브 절을 맨 위에 둔다. 순서 자체가 "judge를 먼저 검증한다"는 규율의 표현이다.

## 하네스 확장 — 집계는 새로 짜지 않는다

**체크리스트 항목 하나는 값이 둘뿐인 분류다.**

```
항목 "근거가 붙었는가"를 3회 물었다 → YES / YES / NO
```

이것은 `EvalAggregator.toCaseResult`가 이미 하는 일이다. 다수결 `YES`, 흔들림 `예`.
범주가 `DAMAGED`냐 `YES`냐만 다를 뿐 로직이 같다. **2026-09-09에 범주를 `ReturnCategory`에서
`String`으로 떼어낸 것이 여기서 값을 한다** — 그때 목적은 메모 분류였는데, 도메인 enum이 아닌
`YES`/`NO`도 그대로 들어간다.

공짜로 따라오는 것이 하나 있다. **흔들림 판정이 곧 judge 신뢰성 관측이 된다.** 같은 브리핑을
세 번 채점했는데 항목이 갈리면 브리핑이 애매한 것이 아니라 judge가 흔들리는 것일 수 있다.

### 새로 만드는 것 (기존 `eval/` 폴더에 `Briefing*` 접두사, 폴더는 나누지 않는다)

| 파일 | |
|---|---|
| `BriefingEvalCase` | 입력 스냅샷 + 네거티브 케이스 표시(어떤 항목이 **떨어져야** 하는지) |
| `GroundingScorer` | 숫자 대조. **모델 없이 도는 진짜 로직이라 단위 테스트 필수** |
| `BriefingEvalTest` | 러너 — 생성 1회 → 사실성 채점 → judge 3회 → 집계 |
| `BriefingReportWriter` | 리포트 |

`EvalAggregator`·`EvalObservation`은 손대지 않는다. 지금 `Memo*` 접두사가 같은 폴더에 있으므로
일관된다.

리소스: `src/test/resources/eval/briefing-snapshots.json`,
`src/main/resources/prompts/briefing-judge.txt`.

## 비용

정상 8건은 생성 1회 + judge 3회 = 32회, 네거티브 4건은 judge 3회만 = 12회. 회당 44회 호출로
지금 메모 분류 평가(90회, 157원)보다 횟수는 작다. 다만 브리핑은 출력 토큰이 분류보다 훨씬 크고
judge는 브리핑 본문을 입력으로 받으므로, **실비는 더 나올 수 있다. 1회차 실측 후 여기에 적는다.**

## 규율

반품 여섯 회차·메모 두 회차에서 값을 치른 것들을 그대로 가져온다.

1. 3회 반복 · 다수결 · 흔들림
2. 한 번에 하나만 바꾼다
3. **1회 관측의 분포 이동에 원인 설명을 붙이지 않는다** — 숫자만이 아니라 설명 문장에도 적용된다
   (메모 1회차에 두 오답을 한 원인으로 묶었다가 2회차에 갈라졌다)
4. 유리한 쪽으로 라벨을 옮겨 점수를 만들지 않는다

## 성공 기준

이 작업이 끝났을 때 답이 나와 있어야 하는 질문들이다. 답을 미리 적지 않는다 — 재서 채운다.

1. **모델이 준 숫자를 그대로 쓰는가, 지어내는가?** (지표 ①·② 실측치)
2. **judge가 망가진 브리핑을 떨어뜨리는가?** 못 떨어뜨리면 유용성 표는 폐기한다.
3. **judge는 자기 출력에 후한가?** 다른 계열 채점과의 차이.
4. **기계 채점과 judge 중 어느 쪽이 더 흔들리는가?** 흔들림 지표로 직접 비교된다.

## 거부한 것

**구조화 출력으로 시작하기.** 모델이 `[{productId, reasonLine}]`만 내고 숫자는 서버가 렌더하면
환각이 구조적으로 불가능하다. 실무적으로는 이쪽이 맞다. **그러나 그러면 사실성 채점이 자동으로
100%가 되어 평가가 배울 것이 없다.** 이 스펙의 목적은 기능이 아니라 측정이므로 A로 시작하고,
실측 후 이쪽으로 옮길지 정한다. 다음 사람이 "왜 처음부터 안전한 쪽으로 안 했나"라고 물으면
이 절을 가리킬 것.

**종합 점수 한 개.** 리포트 절에 쓴 이유로 만들지 않는다.

**judge에게 숫자 정확성을 묻기.** 채점기 1이 확정적으로 답하는 것을 확률적으로 다시 묻는 셈이다.
`PurchaseOrderAdviceService` 주석의 논리("이미 정확한 숫자를 모델에 다시 만들게 하지 않는다")가
채점기에도 그대로 적용된다.
