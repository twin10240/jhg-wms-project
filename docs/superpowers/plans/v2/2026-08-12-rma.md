## 핵심 설계 결정

1. **Reservation FOR UPDATE**: RMA 접수 직렬화의 유일한 잠금 지점. 모든 RMA 생성 경로가 이 잠금을 먼저 획득해야 함
2. **applyDelta 재사용**: RESTOCKED 재고 반영에 기존 경로 사용 → OMS 백오더 승격 통지 자동 발생
3. **OmsReturnStatusNotifier**: OmsReplenishmentNotifier 패턴 복제 — afterCommit + best-effort
4. **RmaResponse 공용**: GET 응답과 OMS 콜백 본문에 동일 DTO 사용
5. **requestKey 멱등**: DB UNIQUE + 내용 비교로 201/200/409 분기

## 리뷰 후 수정 (2026-08-15)

OMS 쪽 검토와 코드 분석에서 나온 4건. 상세는 각 커밋 메시지에 있다.

| 항목 | 내용 |
|------|------|
| 404 계약 | 없는 RMA 조회가 400이었다. `RmaNotFoundException`(IllegalArgumentException 하위)로 404 분리. OMS 보상 스윕이 "요청이 잘못됨"과 "그 rmaId가 없음"을 구분해야 한다. 도달 불가능하던 `IllegalStateException` → 409 핸들러는 삭제 |
| 검수 폼 | 승인 수량 0 + 처분 REJECTED가 기본 선택이라, 손대지 않고 제출하면 전량 거절로 **되돌릴 수 없게** 확정됐다. 기본값 제거·required·서버 미입력 거부·확인창 |
| 권한 표시 | 입고·검수·취소 버튼에 `sec:authorize` 누락 — OPERATOR에게 보이고 누르면 403 |
| DB 예외 | `AdminDataAccessAdvice`가 조회 화면을 자기 자신으로 리다이렉트해 무한 루프. GET은 503 렌더, POST만 목록으로 |

## 미완 — OMS 구현 대기

OMS는 현재 설계·계획 문서만 있고 구현 코드가 없다(`jhg-commerce-project` 2026-08-12 커밋 3건).
반품 신청 화면, `POST /api/returns` 어댑터, `/api/return-status-events` 수신이 생겨야 통합 시나리오를 돌릴 수 있다.
그 전까지 WMS 단독으로 가능한 검증은 curl 계약 스모크뿐이다.
