# 발주 메모 분류 품질 평가

반품 사유 분류 평가([wms-classification-eval.md](wms-classification-eval.md))와 같은 하네스를 쓴다.
다른 것은 셋뿐이다 — 평가셋 파일, 분류기, 범주 목록. 처분(`RmaDisposition`)이 없으므로
리포트가 처분 절을 내지 않는다.

실행: `./gradlew evalTest --tests '*PurchaseOrderMemoEvalTest*'` (`ANTHROPIC_API_KEY` 필요, 1회 약 156원)

**라벨은 Claude가 초안을 쓰고 사람이 검수했다.** 최종 권위는 사람에게 있다.

**평가셋 문구는 시드 스크립트에서 가져오지 않았다.** 시드 메모는 Claude가 지어낸 어휘라
그대로 쓰면 모델이 자기 말투를 채점한다. 프롬프트에 예시로 적힌 문구도 피했다.

### 이 회차에서 판단한 것

**논쟁적으로 표시해 둔 라벨 셋은 사람 판단으로 확정했고, 셋 다 모델이 맞혔다.**

- `uso-04` "어제 주문이 몰려서 바닥났어요" → `URGENT_STOCKOUT`. 원인은 수요 급증이지만
  발주가 난 계기는 결품이고, `DEMAND_EVENT`는 **예정된** 수요라 사후 관측인 이 건이 안 들어간다.
  모델도 `HIGH` ×3. 프롬프트의 "계기 쪽을 고른다" 규칙이 도는 것으로 보인다.
- `dmd-05` "신규 거래처 납품 예정분" → `DEMAND_EVENT`. 우리가 납품하는 쪽이라 수요다.
  `MEDIUM` ×3 — "거래처"라는 단어에 끌리면서도 넘어가지는 않았다.
- `oth-07` "창고 이전 대비해서 미리 넣습니다" → `OTHER`. 창고 사정은 여섯 범주 어디도 아니다.

**틀린 둘은 규칙 결손이 아니라 문장 읽기로 보인다.** `sup-04`의 "안 나온답니다"는 단종 통보인데
모델은 "재고가 없어진다"로 읽었다 — 프롬프트에 `SUPPLIER` 예시로 "단종 통보"가 이미 있는데도
'단종'이라는 단어가 메모에 없어서 못 걸었다. `oth-05`는 협의 상대가 안 적혀 있는데 거래처로 넘겨짚었다.
프롬프트는 이미 "애매하면 `OTHER`를 쓰고 confidence를 낮춰라"라고 지시한다 — 그 지시가 안 먹은 사례다.

**프롬프트는 고치지 않는다.** 1회 관측이다. 반품 평가에서 비싸게 배운 규율 — 1회 관측의 분포
이동에 원인 설명을 붙이지 않는다, 실패 케이스를 보고 정의를 넓히면 과적합인지 알 수 없다.
이 둘이 다음 회차에도 같은 모양으로 틀리는지가 먼저다.

**`LOW` 13회는 전부 `OTHER` 케이스에 붙었고 전부 정답이다.** 반품 평가에서 닫은 질문
("신뢰도 게이팅은 안 한다")과 같은 방향이다 — `LOW`를 숨기면 맞는 분류가 죽는다.

**흔들림 0건은 첫 회차 값이라 아직 재현이 아니다.** 반품은 두 회차가 같은 분포를 낸 뒤에야
"이 셋에서 측정이 재현된다"고 말할 수 있었다. 2회차 전까지 이 수치로 프롬프트를 판단하지 않는다.
